- 배정 기록이 있는 팀원을 삭제하면 DB 제약 충돌로 500 에러가 나던 문제 → 삭제 전 `name_snapshot` 백필로 해결
- 콘티/월스케줄/주차 등 중복 생성 시 원인을 알 수 없는 500만 뜨던 문제 → 전역 예외 처리로 409 + 안내 메시지 반환
- 검수 전(draft) 콘티가 목록/최신 조회에 필터 없이 바로 노출되던 문제 → published만 노출하도록 수정, 수동 생성 기본값도 published로 변경
- 페이지 간 이동 링크가 없어 막다른 화면이 되던 곳 여러 군데(인명부/공지/스케줄 메인, 신규 작성 화면, 에러 화면) 정리

### Phase 5 — 캘린더 (기능 3)

`calendar_events`/`event_participants` CRUD + 특순 단방향 동기화(ERD 3-4). 백엔드 스캐폴딩(`routers/calendar.py`
prefix만 존재)은 비어 있어 처음부터 구현한다. Phase 2의 `schedule_weeks.special_title`/`special_date`/`special_memo`
저장 로직 위에 동기화를 얹는다.

**확정된 설계 결정**
- 화면 형태: **달력 그리드형**(요일×주 그리드, 순수 JS로 계산, 신규 라이브러리 없음). 콘티/공지/스케줄의 "목록+상세페이지" 패턴과 다르게, 캘린더만 월간 그리드로 신규 구현 — 상세/작성/수정은 기존 패턴대로 별도 페이지(`/calendar/:id`, `/calendar/new`, `/calendar/:id/edit`)
- 멀티데이 이벤트: 셀 스패닝(막대 형태)은 하지 않음. `start_date` 셀에만 칩으로 표시, 칩/상세에 `~end_date` 텍스트만 병기
- 자동 동기화 이벤트(`source_type=auto_from_schedule`): 그리드에 일반 이벤트와 같은 목록에 섞어서 표시하되 칩에 별도 배지(링크 아이콘). 상세 페이지는 수정/삭제 버튼 대신 안내문("공지사항(월간 스케줄)에서 수정해주세요") + `/schedules` 링크만 표시 — 일부만 숨기면 캘린더가 "이번 달 전체 일정" 화면이라는 목적과 어긋나기 때문
- 카테고리: 드롭다운 고정값(수련회/엠티/특순/기타) + `기타` 선택 시에만 `category_custom` 텍스트 입력 노출
- 참여 인원(`event_participants`): 인명부 다중 선택(체크박스, Phase 2 콰이어/싱어악보 다중 선택 UI 재사용) + 인명부 밖 인물을 위한 자유 텍스트 추가 행(`name_snapshot`만 저장)
- 특순 동기화 트리거: `special_date`가 있으면 그 값을, 없으면 `service_date`를 이벤트 `start_date`로 사용. `category='특순'` 고정. `special_title`이 비워지면 이벤트 삭제. `source_type='auto_from_schedule'` 행은 직접 API로 생성/수정/삭제 불가(403) — ERD 3-4/API명세 3절 그대로

   생성/수정 겸용 폼. 제목/시작일/종료일(선택)/카테고리 드롭다운(+기타 조건부 입력)/메모/참여 인원(인명부 다중 선택 + 자유 텍스트 추가 행) + 비밀번호 입력 후 저장. auto 이벤트 id로 진입 시 폼 대신 안내 문구만 표시(방어적 처리).

10. **라우팅**
    `App.jsx`에 `/calendar`, `/calendar/new`, `/calendar/:eventId`, `/calendar/:eventId/edit` 추가.

11. **확인/빌드**
    `uvicorn` 재기동 확인, `/docs`에서 캘린더 5개 엔드포인트 호출 테스트 + 스케줄 주차 PATCH로 `special_title`을 넣었다 뺐다 하며 캘린더 자동 upsert/삭제 확인 → `npm run dev`로 그리드/상세/작성/삭제 흐름 + auto 이벤트 수정 시도 시 안내문 확인 → `npm run build` 통과 확인.

### Phase 6 — AI 콘티 이미지 인식 ✅ 완료 (2026-08-20)

콘티 이미지를 OpenAI vision 모델에 1회 호출해 곡 순서·제목·아티스트·키·송폼을 JSON으로 추출하고,
**사람이 검수한 뒤** Phase 1의 곡 배치 저장 API(`PUT /contis/{id}/songs`)로 확정한다.
추출 결과는 `ai-parse` 단계에서 DB에 저장하지 않는다(API명세 1-4).

**선행**: `OPENAI_API_KEY` 발급·설정 — 원래 설계는 Claude vision이었으나, 테스트 기간 동안 제공받은
OpenAI 키를 사용하기로 변경(2026-08-20). README/문제정의-재료의 "비전 지원 LLM API(Claude/GPT 등)" 표현은
원래도 특정 벤더에 종속되지 않아 별도 수정 불필요. 키는 `backend/.env.local`에 이미 설정됨(git 비추적).

**착수 전 확인한 현재 상태**
- `backend/app/config.py`에 `ANTHROPIC_API_KEY`만 있고 `OPENAI_API_KEY`는 로드되지 않음 → 교체 필요
- `requirements.txt`에 `openai` 없음 → 추가 필요
- `PUT /contis/{id}/songs`가 이미 `new_song` 동시 생성을 지원 → 검수 저장은 이 API 그대로 재사용, 신규 저장 API 없음
- `ContiEdit.jsx`가 `/conti/new`(생성)와 `/conti/:id/edit`(편집)을 한 컴포넌트로 겸용 중 → 검수 UI를 여기에 얹음

**확정된 설계 결정 (2026-08-20)**
- **검수 UI는 기존 `ContiEdit.jsx`에 통합** — `/conti/new` 상단에 "콘티 이미지로 시작하기" 업로드 섹션을 추가하고,
  인식 결과가 기존 곡 입력 폼(rows)을 채운다. 그 아래 저장 흐름은 지금과 100% 동일. 신규 페이지·라우트를 만들지 않는 이유는
  ① 곡 행 편집 UI를 중복 구현하지 않아도 되고 ② 페이지 간 인식 결과 전달(navigate state) 상태 관리가 필요 없기 때문.
  편집 화면(`/conti/:id/edit`)에서도 같은 섹션으로 곡 목록을 이미지로 덮어쓸 수 있다
- **status 흐름은 draft → published** — "AI로 인식" 성공 시 콘티 레코드를 `status='draft'`로 먼저 만들고
  `/conti/:id/edit`로 이동, 검수 후 "게시" 버튼으로 `published` 전환. API명세 1-1에 명시된 draft의 유일한 실사용 시나리오와 정확히 일치하며,
  검수 중 이탈해도 결과가 남는다. **알려진 한계**: 검수를 포기하면 빈 draft가 남고, 로그인이 없어 draft 목록 화면이 없으므로
  URL(ID)을 기억해야 정리할 수 있다 — 이번 범위에서는 draft 조회 API를 추가하지 않고 한계로 남긴다
- **원본 이미지 보관은 체크박스 선택** — 업로드 섹션에 "원본 이미지도 함께 보관"(기본 켜짐). 켜져 있으면 검수 확정 시
  해당 이미지를 `sheet_files`에 `file_type='conti_image'`로 저장한다. AI가 무엇을 보고 이렇게 뽑았는지 대조할 수 있어
  트러블슈팅 기록(산출물)에 활용 가능
- **프롬프트 추출 범위는 곡 정보 + 날짜/제목 + note** — 제목·아티스트·키·송폼에 더해 헤더 줄(`260809 4부예배 콘티`)에서
  날짜·제목을 추정하고, `<축복송>`/`<퇴장송>` 같은 꼬리표를 `note`로 분리한다. README 부록 B의 원본 예시가 이 형태를
  모두 갖고 있고, 어차피 사람 검수가 필수라 틀려도 리스크가 낮다
- **송폼은 해석·정규화 금지** — 프롬프트에 "송폼 문자열은 이해하거나 재구성하지 말고 원문 그대로 옮기라"고 명시(README 기능 1 기대치와 동일)
- **곡 매칭은 서버가 수행** — ERD 3-1대로 정규화된 제목(공백·특수문자 제거, 소문자화) **완전 일치**로만 기존 `songs` 후보를 찾고,
  없으면 신규 곡으로 제안한다. 유사도 기반 자동 매칭은 하지 않으며, 최종 확정("기존 곡 선택 / 새로 등록")은 검수 화면에서 사람이 한다.
  프론트가 곡 목록 전체를 받아 비교하지 않도록 응답에 매칭 결과 필드를 포함한다
- **신규 의존성 `openai` 추가**(CLAUDE.md 규칙상 확인받은 항목) — `httpx`로 직접 구현하면 이미지 base64 인코딩·모델 파라미터·
  에러 분류를 전부 직접 관리해야 하고, 공식 SDK 사용이 프로젝트의 "AI 연동은 파이썬 생태계 활용" 스택 선정 근거와도 부합
- **에러/제약 기본값**: 허용 포맷 `image/png|jpeg|webp`, 최대 8MB(초과 시 400) / OpenAI 타임아웃 60초 → 504 /
  API 오류·레이트리밋 → 502 + "AI 인식에 실패했습니다. 다시 시도하거나 직접 입력해주세요" /
  **인식된 곡이 0개여도 에러가 아니라 빈 배열 반환** — 사람 검수가 필수 단계라 부분 인식도 그대로 유용하기 때문

**계획에서 바뀐 것 — 인식 결과를 곧바로 저장하지 않는다**
SDD에서는 인식 직후 draft 콘티를 만들면서 곡 배치까지 저장할 생각이었으나, 구현 중 문제를 발견해 바꿨다.
AI가 곡 제목을 잘못 읽으면(실제로 `전신갑주` → `전심감주`, `위러브` → `워리브` 오인식 발생) 그 오타가 **곡 마스터에 영구히 남는다.**
사람이 고쳐도 새 행이 하나 더 생길 뿐 잘못된 행은 남고, 나중에 `songs UNIQUE(title, artist)` 충돌의 원인이 된다.
ERD 3-1이 "기존 곡 선택 / 새로 등록을 사람이 확정"하라고 못 박은 지점이라, 인식 결과는 화면 상태로만 넘기고(`navigate(..., { state })`)
**사람이 확인한 뒤 저장**하도록 했다. 콘티 레코드(날짜·제목·id)·원본 이미지·`ai_raw_result`는 인식 즉시 저장되므로 이탈해도 초안은 남는다.

**계획에 없던 추가 작업 3건**
- `ContiCreate.status` 추가 — 확정된 "인식 직후 draft 생성"을 지원할 백엔드 수단이 없었다. 생성 후 `PATCH`로 draft로 되돌리면 그사이 팀 전체에 잠깐 노출된다.
- **Storage 고아 파일 버그 수정** — `DELETE /contis/{id}`가 DB의 `sheet_files` 행만 CASCADE로 지우고 Supabase Storage의 실제 파일은 남겨왔다(Phase 1부터 있던 버그, 고아 파일 4건 확인 후 정리). 콘티 삭제 직전에 Storage 파일을 정리하도록 수정했고, 업로드 API에 `replace` 옵션을 넣어 AI 재인식 시 원본 이미지가 한 장만 유지되게 했다.
- **검수 대기 목록 + 곡 관리 화면** — 로그인이 없어 방치된 draft를 찾을 방법이 없고, 곡 삭제 수단이 아예 없어 잘못 만들어진 곡을 지우려면 DB에 직접 들어가야 했다. `GET /contis?status=draft`와 `DELETE /songs/{id}`(사용 중이면 409)를 추가하고, `/conti`에 "검수 대기" 섹션과 `/songs` 곡 관리 화면을 붙였다.

**실제 인식 정확도**: 날짜(`260809` → `2026-08-09`)·제목·곡 순서·키·송폼 원문(`bis(주 사랑만이~)*2`, `Tag(...)`, `C**`, 작은따옴표 반복 표기)·`<축복송>`/`<퇴장송>` note 분리까지 기대대로 동작했다. 다만 **아티스트명은 호출할 때마다 흔들린다**(`위러브` → `워리브` 등). README가 예상한 그대로라 프롬프트로 해결하지 않고 검수 화면에서 잡는 것으로 뒀다. 실제 카톡 콘티 이미지로 한 번 더 확인해볼 여지가 있다.

**트러블슈팅**: `uvicorn --reload`가 연속된 파일 수정 중 일부를 놓쳐 옛 코드로 응답하는 일이 있었다. Storage 수정 2건이 동시에 실패해 코드를 의심했는데, Swagger(`/openapi.json`)에 새 필드가 없는 것을 보고 서버가 stale임을 확인 — 재기동 후 정상 동작했다. Phase 1의 포트 점유 문제와 같은 계열이라, 백엔드 수정 후에는 **Swagger로 반영 여부를 먼저 확인**하는 편이 빠르다.

**문서 동기화 완료**: API명세 1-1(draft 목록·`status` 생성 옵션)/1-2(곡 삭제·`usage_count`)/1-4(응답 스키마·에러·제약)/1-5(`replace`·Storage 정리)/2-2(누락돼 있던 `DELETE /schedules/{id}`)/5절 총계(31 → 36)를 실제 Swagger와 대조해 갱신했다. DB 스키마 변경은 없어 ERD·schema.sql은 그대로다.

### Phase 6 후속 — AI 인식 정확도 개선 + 검수 보조 ✅ 완료 (2026-08-20)

Phase 6 완료 후 사용자가 제안한 두 가지("곡 드롭다운 검색 + 유사도 추천", "인식 정확도 개선")를 다뤘다.
"간단한 예측 모델 학습"은 배제했다 — 콘티는 주 1건이라 라벨 데이터가 수십 건 수준이고, 무거운 의존성이
필요하며, 남은 일정(8/28 마감, Phase 7 미착수)에 맞지 않는다. 대신 같은 목적을 프롬프트·후처리·UI로 달성했다.

**먼저 측정 기반부터 만들었다.** 그때까지의 오인식 관찰은 전부 합성 이미지 기준이라 개선을 숫자로 말할 수 없었다.
실제 콘티 이미지 5장(주일예배 4 + 특새 1, 곡 27건)의 정답을 사람이 만들고, 필드별 정확도를 출력하는
`backend/tests/ai_parse_baseline.py`를 작성했다. 이미지·정답은 팀 내부 자료라 `tests/fixtures/`에 두고 gitignore 처리.

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 날짜 | 3/5 | **5/5** |
| 곡 제목 | 93% | **96%** |
| 아티스트 | 89% | **96%** |
| 키 / note | 100% | 100% |
| 송폼 | 81% | 81~85% |
| **전체** | **92.6%** | **94.8%** |

**적용한 개선**
- **날짜는 서버가 계산** — 모델에게 변환까지 맡기니 `260816`을 `2016-08-26`으로 자리를 바꿔 읽었다(5장 중 2장).
  헤더 6자리 원문만 받아 서버에서 변환하도록 바꿔 확률적 개선이 아닌 **결정론적 해결**이 됐다.
- **`temperature=0`** — 지정하지 않아 기본값 1.0으로 돌고 있었다. 옮겨 적는 작업에 무작위성은 손해만 된다.
- **프롬프트에 기존 곡 목록 주입** — 같은 곡이 매주 반복되는 팀 특성을 이용. 송폼은 의도적으로 제외했다
  (지난주 송폼을 베끼면 이 프로젝트가 없애려는 문제가 그대로 재발한다).
- **`detail: "high"`는 측정 후 폐기** — 94.8% → 94.1%로 오히려 떨어졌고 토큰만 더 썼다. 코드에 근거를 주석으로 남김.

**검수 보조 UI (남은 오류를 사람이 잡게)**
송폼 81%는 프롬프트로 더 내려가지 않았다(`호흡있는`→`흐름있는`, `(8)` 누락 등 작은 글자 오독). 원본이 730px 폭이라
해상도 한계로 보이며, 모델을 바꾸지 않는 한 한계다. 그래서 화면에서 잡도록 세 가지를 붙였다.
- **곡 검색(`SongPicker`)** — 곡 마스터는 매주 쌓이는데 `<select>`에 전곡을 넣고 있었다. 검색 입력으로 교체하고,
  이미 고른 곡은 접어서 제목만 표시한다(검수 화면에 곡이 6줄씩 늘어서므로).
- **유사 곡 후보** — 완전 일치가 없을 때 자모 유사도(NFD + difflib)로 최대 3개 제안. 자동 적용하지 않는다(ERD 3-1).
- **지난번 송폼 비교(`SongFormDiff`)** — 매칭된 곡의 지난 송폼과 토큰 단위 LCS diff로 달라진 부분만 강조하고
  "지난번 송폼으로 되돌리기"를 제공한다. 대부분의 주는 지난주와 송폼이 같아 **바뀐 행만 눈에 띄는** 구조다.
  실제 재인식에서 6곡 중 Praise 한 줄만 비교 박스가 떴고, 거기서 `(8)` 누락과 `호흡있는`→`흐름있는`이 드러났다.

**발견한 것 — 곡 목록 힌트는 양날의 검**
검증 중 곡 마스터의 제목을 일부러 `십자가 이야기` → `십자가 이야가`로 바꿔놓고 인식시켰더니,
**AI가 이미지의 올바른 글자 대신 힌트 속 틀린 제목을 그대로 따라 읽었다.** 힌트가 잘 작동한다는 증거인 동시에,
잘못된 제목이 마스터에 한 번 저장되면 이후 인식이 계속 그 오타를 재생산한다는 뜻이다.
→ 곡 관리 화면(`/songs`)에 제목·아티스트·기본 키 수정 UI를 추가해 바로 고칠 수 있게 했다(기존에는 삭제만 가능).

**남은 개선 여지**: 송폼 오독은 모델·해상도 문제라 프롬프트로는 한계다. 실사용하며 오류가 반복되면
다른 vision 모델로 `OPENAI_VISION_MODEL`만 바꿔 같은 스크립트로 재측정하면 비교가 된다.

### Phase 7 — 정식 로그인 / 리더십 역할 구분 ✅ 완료 (2026-08-20)

일정에 여유가 생겨 원래 "여유 시" 항목이었던 로그인을 정식 구현하기로 확정(2026-08-20). Phase 6(AI 콘티 이미지 인식) 완료 후 착수한다.
지금까지 인증은 `backend/app/dependencies.py`의 `verify_edit_password` 함수 **하나**가 전담하고, 7개 라우터(콘티/곡/파일/공지/스케줄/캘린더/인명부)의
쓰기 엔드포인트 **26곳**에 `Depends(verify_edit_password)`로 걸려 있다. 프론트는 세션 개념 없이 편집 화면 7곳이 각자 `password` state를 들고
저장할 때마다 사람이 다시 입력한다. 이 구조 전체를 건드리는 변경이라 아래 SDD를 먼저 확정했다.

#### 확정된 설계 결정 (2026-08-20, 사용자 확인)

| 항목 | 결정 | 근거 |
|---|---|---|
| 로그인 수단 | **이메일 + 비밀번호** | Supabase Auth 기본 기능만 쓰면 되고 외부 심사·도메인 등록이 없다. 매직링크는 SMTP·무료 발송 한도, 카카오 OAuth는 개발자 앱 등록·리다이렉트 도메인 심사가 걸려 8/28 마감 전 일정 리스크가 가장 크다 |

| 비로그인 조회 | **지금처럼 전체 공개 유지** | README 6절 "초대 링크만 알면 누구나 조회"를 바꾸지 않는다. 22명이 계정을 안 만들어도 서비스가 그대로 돌아가야 8월 말 실사용 테스트의 배포 마찰이 없다 |
| 계정 생성 | **앱 내 회원가입 → 무조건 `member`** | 가입 자체는 자유롭게 두되 권한이 0이라 안전하다. `leader` 승격은 `admin`이 전용 화면에서 부여. 승인 대기(pending) 상태를 만들지 않아 화면·상태가 하나 줄어든다 |
| role 저장 | **신규 `user_profiles` 테이블** | `auth.users.id`(uuid) PK + `role` + `display_name` + `member_id`(nullable FK). 인명부(`members`)는 "배정 드롭다운용 마스터 데이터"라 성격이 다르고, 계정과 1:1도 아니다(탈퇴자·`01우진` 같은 동명이인 구분 행이 이미 있다). members에 컬럼을 얹으면 인명부 삭제가 계정 권한을 날리는 결합이 생긴다 |
| 기존 게이트 | **완전 대체 — `EDIT_PASSWORD` 제거** | 처음엔 `AUTH_MODE` 스위치 병행을 검토했으나, 진행 속도상 로그인을 끝까지 완성할 여유가 있다고 판단해 **2026-08-20 완전 대체로 확정**. 병행은 백엔드 분기 + 프론트 조건부 렌더(`EditAuthGate`)를 양쪽에 남겨야 해서, 없애려는 옛 방식이 코드에 계속 살아 있는 대가가 컸다 |
| 로그인 UX | **전용 `/login` 페이지 + 세션 유지** | 저장할 때마다 비밀번호를 다시 치던 마찰을 없앤다 |
| 권한 없는 편집 진입 | **`/login` 리다이렉트 + 편집 버튼 숨김** | 비밀번호 칸이 사라지므로, 권한이 없는 사람에게 빈 편집 폼을 보여주면 무엇이 문제인지 알 수 없다. 조회 화면에서는 버튼 자체를 감추고 URL 직접 진입만 가드가 막는다 |

**ERD 3-5는 무효화되지 않는다.** "편집용 비밀번호를 테이블로 두지 않는다"는 근거는 *값이 하나뿐이고 변경 빈도가 없는 비밀번호*에 대한 것이고,
지금 테이블로 만드는 것은 비밀번호가 아니라 **사람별 역할**이다. 비밀번호 자체는 여전히 우리 스키마에 없다 — 계정 비밀번호는
Supabase Auth(`auth.users`)가 해시해 보관하고, `EDIT_PASSWORD` 환경변수는 이번에 아예 사라진다.

#### fallback 원칙의 재정의 (README 6절)

README 6절은 "실패·시간 부족 시 **비밀번호 방식이 반드시 완성하는 최소 기준(fallback)**"이라고 적어뒀다. 완전 대체를 택한 이상
그 문장은 구현과 어긋나므로, fallback을 **"Phase 7 커밋을 되돌리면 Phase 6 상태로 복귀한다"** 로 재정의한다.

- 이 재정의는 문서 수정이 아니라 **작업 조건**이다. Phase 7의 커밋을 되돌리기 쉬운 경계로 관리하고(백엔드/프론트/문서를 섞지 않음),
  8번 "26곳 의존성 교체" 커밋을 되돌리면 그 즉시 비밀번호 게이트가 살아나도록 순서를 짠다.
- `EDIT_PASSWORD`는 코드에서 지우되 **`backend/.env.local`의 값은 Phase 8 배포까지 지우지 않는다.** revert 후 값이 없으면 되돌려도 동작하지 않기 때문이다.
- 16번에서 README 6절 표의 fallback 행을 이 정의로 갱신한다.

#### SDD가 정하고 넘어가는 파생 결정 2가지

1. **로그인은 프론트가 Supabase에 직접 붙지 않고 FastAPI를 경유한다.** `supabase-js`를 프론트에 추가하면 CLAUDE.md의
   "Frontend-Backend는 REST API로만 통신" 원칙과 "불필요한 라이브러리 추가 금지"에 동시에 걸린다. `POST /auth/login`이 백엔드에서
   Supabase Auth를 호출해 토큰을 돌려주는 형태로 두면 **프론트 신규 의존성이 0개**고, 백엔드도 이미 `supabase` 파이썬 클라이언트를 쓰고 있어 추가 설치가 없다.
2. **토큰 검증은 `auth.get_user(jwt)` 호출로 한다.** JWT 서명을 직접 검증하려면 `pyjwt`라는 신규 의존성이 붙는다.
   요청당 Supabase 왕복 1회가 늘지만 22명 규모에서 체감 차이가 없고, 의존성 0개가 남은 일정에서 더 값싸다. 느려지면 그때 캐시를 얹는다.

##### Backend

#### Phase 7 후속 — 비밀번호 초기화(관리자) + 강제 변경 + 아이디 기억하기 (2026-08-20)

실사용자(사용자 본인)가 로그인 테스트 중 두 가지를 요청했다.
1. 비밀번호를 잊으면 어떻게 하나 — 이메일 재설정 링크 방식은 회원가입 이메일 인증과 같은 SMTP/발송한도 문제를 그대로 안는다.
2. 로그인 상태 유지 — 이미 구현돼 있었음(세션은 항상 localStorage에 유지되고 401 시 자동 refresh, Phase 7 본 작업의 일부).

**처음 제안한 방식(관리자가 새 비밀번호를 직접 입력)은 사용자가 보안 문제를 지적해 기각했다** — 그 방식은 관리자가 팀원의 새 비밀번호를 알게 된다.
대신 다음 흐름으로 확정:
- 관리자가 "비밀번호 초기화" 버튼만 누르면 **서버가 무작위 임시 비밀번호를 생성**해 응답에 1회만 담아 돌려준다(관리자도 값을 직접 정하지 않음).
- 그 사용자는 `user_profiles.force_password_change`가 `true`로 켜져, 임시 비밀번호로 로그인하는 순간 프론트가 어떤 경로로 이동을 시도해도 `/change-password`로 강제 리다이렉트한다(`App.jsx`의 `ForcePasswordChangeGuard`).
- 본인이 새 비밀번호로 바꾸면(`POST /auth/me/password`) 플래그가 꺼지고, **그 순간부터는 관리자도 새 비밀번호를 모른다.**
- "아이디 기억하기" 체크박스도 함께 추가 — 이메일만 `localStorage`에 남기고(비밀번호는 저장 안 함) `/login` 재방문 시 자동으로 채운다.

**작업 내역**: `user_profiles.force_password_change` 컬럼 추가(`schema.sql` 동기화, 사용자가 SQL Editor에서 직접 실행) →
`POST /auth/users/{id}/password`(admin, 임시 비밀번호 생성·반환) · `POST /auth/me/password`(본인, 변경) 엔드포인트 신설 →
`AdminUsers.jsx`에 초기화 버튼 + 발급된 임시 비밀번호 1회 표시 UI, `ChangePassword.jsx` 신규, `App.jsx`에 `ForcePasswordChangeGuard` 추가, `Login.jsx`에 기억하기 체크박스.

**검증**: 로컬 dev 서버(백엔드 8003, 포트 8001 유령 리슨 문제로 지난 세션과 동일하게 우회) + Playwright로
관리자 로그인 → `/admin/users`에서 초기화 → 임시 비밀번호로 로그인 시 어느 경로로 가도 `/change-password` 유지 →
본인 변경 → 이후 자유 이동 및 새 비밀번호 재로그인까지 확인했다(스크린샷·콘솔 에러 0건). 테스트 계정은 모두 정리했다.
문서: API명세 4-1절(엔드포인트 2개 추가, 42→44), ERD 엔티티·3-6절, `schema.sql` 갱신 완료.

#### Phase 7 후속 — 회원가입 비밀번호 확인 + 내 정보(표시 이름) 수정 (2026-08-20)

로그인/가입 표준 기능 중 이 프로젝트 규모(22명 폐쇄형 팀)에 실제로 마찰을 줄여줄 두 가지를 사용자에게 제안해 확정했다.
이메일 인증·재설정 링크, 로그인 시도 제한, 소셜 로그인, 가입 승인 대기 등은 기존 SDD 결정과 겹치거나 실사용 이득이
적어 제안하지 않았다(README/SDD의 배제 사유와 동일 선상).

- **회원가입 비밀번호 확인 칸**: `Signup.jsx`에 비밀번호를 한 번만 입력받던 것을 `ChangePassword.jsx`와 동일한
  확인 입력 패턴으로 맞췄다. 오타로 가입해놓고 원인을 모른 채 로그인이 안 되는 문제를 막는다.
- **본인 표시 이름 수정**: 가입 후 이름을 바꾸려면 관리자가 SQL로 고쳐야 했던 문제(실제로 "손지헌" 계정에서
  겪음)를 없앴다. `PATCH /auth/me`(본인, `display_name` 변경) 엔드포인트 신설 + `/profile`("내 정보") 화면 신규.
  헤더의 "비밀번호 변경" 링크는 "내 정보"로 통합하고, 비밀번호 변경은 그 화면 안에서 이어지도록 정리했다.

**검증**: Playwright로 회원가입 시 비밀번호 불일치 검증 메시지 → 정정 후 가입 성공 → `/profile`에서 이름 변경 →
헤더에 즉시 반영까지 확인했다(콘솔 에러 0건). 문서: API명세 4-1절(엔드포인트 1개 추가, 44→45).

#### Phase 7 후속 — 계정 이벤트 로그 (2026-08-21)

사용자가 "admin이 닉네임 변경 등 계정 관련 변화를 이력으로 볼 수 있으면 좋겠다"고 제안했다. 전체 CRUD를
추적하는 범용 감사로그는 이 프로젝트 스코프(10일, 핵심 기능 3개 원칙)를 벗어나는 엔지니어링이라 제안하지
않았고, 대신 admin이 실제로 손대는 **계정 보안 이벤트 3가지**(표시 이름 변경, 역할 변경, 비밀번호 초기화)만
좁혀서 로그로 남기는 것으로 범위를 정했다(2026-08-21 사용자 확인). Phase 10(댓글)과는 건드리는 코드 영역이
겹치지 않아(이건 `auth_service.py`/`AdminUsers.jsx`, Phase 10은 `notices.py`/`calendar.py`) 되돌림 경계를
깔끔하게 유지하기 위해 Phase 10보다 먼저 별도로 완결했다.

**신규 테이블 `account_events`**: `user_id`(대상 계정) + `event_type`(`display_name_changed`/`role_changed`/
`password_reset`) + `old_value`/`new_value` + `changed_by`/`changed_by_name`(실행자, 작성 시점 이름 스냅샷) +
`created_at`. **`password_reset`은 `old_value`/`new_value`를 항상 `null`로 둔다** — 비밀번호 값 자체는
Phase 7부터 지켜온 "관리자도 저장하지 않는다" 원칙을 그대로 따른다. RLS는 다른 테이블과 동일하게 활성화 +
정책 없음.

**신규 엔드포인트 1개**: `GET /auth/users/{user_id}/events`(admin 전용, 최신순) — API명세 총계 48 → 49.

**기록 지점**: 기존 서비스 함수 3개(`update_display_name`, `update_role`, `reset_password`)에 이벤트 기록
호출만 추가했다. 새 엔드포인트를 만들지 않고 기존 흐름에 얹는 방식이라 프론트의 기존 호출부(`AdminUsers.jsx`,
`/profile` 화면)는 수정할 필요가 없었다. `update_role`/`reset_password`는 admin이 실행하는 액션이라 라우터에서
`current_user`(actor)를 받아 서비스로 넘기도록 시그니처를 바꿨다(`actor_id: str` → `actor: UserProfile`).
`update_display_name`은 본인이 실행하는 액션이라 `changed_by`/`changed_by_name` 모두 본인 값을 쓴다.

**UI**: `/admin/users`의 사용자 행마다 "이력 보기" 토글을 추가했다. 펼치면 `[역할 변경] 팀원 → 리더십
(관리자 이름, 시각)` 형태로 렌더링되고, 사용자별로 한 번 불러온 이력은 캐시해 다시 펼칠 때 재조회하지 않는다.

**검증**: 백엔드 `python -c "from app.main import app"`로 임포트·라우트 등록 확인, `npm run build` 통과 확인.
실 DB 반영(Supabase SQL Editor에서 `account_events` 테이블 생성)과 실제 이름 변경/역할 변경/비밀번호 초기화
흐름에서 이력이 쌓이는지는 사용자가 다음 접속 시 직접 확인.

- 2026-08-20 견적 검토 때 실제 송폼 27건(토큰 336개)을 분석해 "약 95%가 정규식 수준 패턴"임을 확인했다. 아래 파서 사양이 그 분석 결과다.

**파생 결정 (SDD가 정하고 넘어간다)**

6. **조합은 백엔드 서비스에서 한다.** 프론트에서 조립하면 파싱 규칙이 화면 코드에 흩어지고 테스트가 어렵다. 파서를 순수 함수 모듈로 두면 실제 송폼 27건으로 `pytest` 회귀 테스트를 붙일 수 있다(Phase 6의 `ai_parse_baseline.py`가 정확도를 숫자로 관리한 것과 같은 접근).
7. **조합 결과는 DB에 저장하지 않는다.** 매 요청마다 `song_sections` + `conti_songs.song_form`으로 계산한다. 저장해두면 가사를 고친 뒤 자막 결과가 옛날 값으로 남는, **이 프로젝트가 없애려는 "원본과 사본 불일치" 문제가 그대로 재발**한다. 곡 6개 × 구간 몇 개 수준이라 계산 비용은 무시할 만하다.
8. **신규 의존성 0개.** 파서는 표준 `re`만 쓰고, 프론트도 추가 라이브러리 없이 기존 패턴을 재사용한다.

#### 송폼 토큰 문법 (파서 사양)

송폼을 공백으로 토큰화한 뒤 아래 5종으로 분류한다. 실제 데이터(README 부록 B + 콘티 27건)에서 관찰된 표기가 전부다.

| 유형 | 실제 예 | 판별 | 조합 시 처리 |
|---|---|---|---|
| 구간 참조 | `A` `A1` `A2` `B` `C*` `C**` `B'` `B'''` | `^[A-Za-z][0-9]*['*]*$` | `song_sections`에서 가사 조회 → 가사 블록. **정확 일치 우선, 없으면 `*`·`'` 접미사를 떼고 재조회**하고 "변주 표기(A* → A)"를 주석으로 남긴다 — 접미사는 같은 구간의 변주라 별도 가사가 아닌 경우가 대부분이다 |
| 마디/간주 | `(4)` `(8)` `(12)` `(맞4)` `(맞8)` `(up)` | 괄호 안이 숫자·`맞n`·`up` | 가사 없는 **마커 블록**. 지우지 않고 원문 그대로 남긴다 — 자막팀이 넘길 타이밍을 아는 근거이기 때문 |
| 반복 | `x2` `*2`, 앞 토큰에 붙은 `*2` | `^[x*]\d+$` 또는 접미사 | 직전 블록을 n회 반복하고 "반복 ×n" 주석 |
| 인용 딸린 지시 | `bis(주 사랑만이~)*2` `Tag(나의 노래로~받으소서)` | `^(\S+?)\((.+)\)([x*]\d+)?$` | 앞부분이 등록된 구간 코드면(`Tag` 등) 그 구간 가사를, 아니면 **괄호 안 인용을 그대로** 블록으로 삼고 "인용 표기(축약)" 주석. 인용은 `~`로 줄인 형태라 가사 전문으로 확정하지 않는다 |
| 미해결 | `Let Everything` `호흡있는` (가사 첫 구절이 토큰인 경우), 등록 안 된 구간 코드 | 위 어디에도 해당 없음 | `[?] 원문` 그대로 남기고 미해결 카운트 증가 |

> **미해결을 사람이 흡수하는 경로**: `song_sections.section_code`는 `text`라 `A1` 같은 코드뿐 아니라 `Let Everything` 같은 문구도 그대로 코드로 쓸 수 있다. 그래서 결과 화면의 미해결 토큰마다 "이 문구로 구간 만들기" 링크를 붙여 구간 등록 화면으로 보낸다. **한 번 등록하면 그 곡이 다음에 나올 때부터 자동 해결**되므로, 5% 케이스가 쓸수록 줄어드는 구조가 된다. 파서를 더 똑똑하게 만드는 대신 사람이 한 번 채우게 하는 쪽을 택한 이유다(ERD 3-1의 "누적 재사용" 설계와 같은 방향).

#### 신설 엔드포인트 (3개 — API명세 총계 45 → 48)

| Method | Path | 설명 | 인증 |
|---|---|---|---|
| GET | `/songs/{song_id}/sections` | 곡의 구간별 가사 목록 | **member 이상** |

**남은 리스크**
1. **가사 입력은 결국 사람 노동이다.** 곡당 1회지만 첫 콘티(6곡)를 처리하려면 초기 입력 시간이 든다 — 자주 나오는 곡부터 채우면 몇 주 안에 재사용률이 올라간다는 것이 이 설계의 전제다.
2. **`section_code` 표기가 콘티마다 흔들리면**(`A1`으로 등록했는데 이번 주 송폼은 `A`) 미해결이 늘어난다. 접미사 폴백과 "이 문구로 구간 만들기" 경로로 흡수하되, 실사용에서 빈도가 높으면 그때 정규화 규칙을 추가한다.
3. **저작권은 로그인 게이트로 완화될 뿐 해소되지는 않는다.** 팀 내부용 폐쇄 서비스라는 전제 위의 판단이므로, Phase 13에서 외부에 공개 배포하거나 포트폴리오로 시연할 때 이 화면을 어떻게 다룰지 다시 확인해야 한다.
4. **AI 구간 제안(Phase 9 후속)은 이번 범위 밖**이다. 위 1~7번이 다 동작한 뒤, 가사 전문을 텍스트 모델에 넣어 A/B/C 구간 분할을 제안받고 사람이 검수하는 형태로 얹는다.

**실제 진행 결과 (2026-08-21)**: SDD의 작업 분해를 기능 단위 4개 묶음으로 재편해 구현했다 — 묶음 A(파서 코어: `song_form_parser.py` + 실제 송폼 예시 기반 pytest 11건, README에 이미 공개된 표기만 사용해 팀 가사 데이터 없이 git에 올릴 수 있는 첫 테스트가 됨) → 묶음 B(조합 서비스 `lyrics_service.py` + API 2개 연결) → 묶음 C(곡 구간 입력 UI, `SongMain`에 배지 추가) → 묶음 D(자막 결과 보기 UI, `ContiDetailView`에 링크 추가). 계획과 달라진 점은 없었다.

**흐름 검증(묶음 E)**: 실 Supabase DB에 테스트 계정·곡·콘티를 만들어 구간 미등록→해결/변주 폴백/반복 전개/인용 축약/비로그인 401/구간 코드 중복 400/`section_count` 배지까지 전부 확인 후 정리했다. 검증 중 발견한 유일한 문제는 코드 결함이 아니라 로컬 테스트 포트에 이전 세션의 유령 프로세스가 남아 있던 환경 문제였다(Phase 1·6에서도 겪은 패턴, 포트 정리로 해결). 문서(README 5·6·10·11절, API명세 0-1·1-2·1-6·5절, ERD 엔티티 표·3-1·3-7절)도 실제 구현과 맞춰 동기화했다.

#### Phase 9 후속 — 실사용 피드백 반영 (2026-08-21)

실사용자(리더)가 직접 테스트하며 요청한 개선 사항을 이어서 반영했다.

- **구간 코드 프리셋 드롭다운**: 자유 텍스트 입력 대신 자주 쓰는 코드(`A`, `A1`, `A2`, `B`, `B1`, `B2`, `C`, `Tag`, `Intro`, `Outro`, `Bridge`) 드롭다운 + "기타(직접입력)"으로 변경 — `CalendarEdit`의 카테고리 드롭다운과 같은 패턴을 재사용해 오타로 인한 매칭 실패를 줄였다.
- **`song_sections.aliases` 컬럼 추가**: "같은 곡이라도 상황에 따라 송폼 표기가 바뀔 수 있다"는 실사용 지적에 대응 — 한 구간에 다른 표기를 여러 개 연결할 수 있게 했다(예: `A1` 등록 시 별칭에 `A` 추가). 가사를 복제 저장하지 않고 표기만 여러 개 등록하는 방식이라 원본-사본 불일치 문제가 재발하지 않는다. `lyrics_service`의 매칭 우선순위를 정확 코드 → 별칭 → 변주 접미사 폴백 순으로 확장했고, 구간 코드/별칭 전체를 하나의 이름공간으로 봐서 중복 시 400으로 막는다.
- **`GET/PUT /songs/{id}/sections` 응답에 `last_song_form` 힌트 추가**: 이 곡이 최근 콘티에서 쓰인 송폼 원문을 구간 등록 화면에 보여줘, 어떤 코드로 등록해야 할지 감을 잡기 쉽게 했다(기존 `song_repository.find_last_song_forms` 재사용, 신규 로직 없음).
- **미해결 표기 프리필**: 자막 결과 화면의 미해결 블록마다 "이 표기로 구간 등록" 링크를 추가해, 클릭 시 원문이 구간 등록 화면에 자동으로 채워지도록 했다(`?prefill=` 쿼리).
- **파트 간 여백/들여쓰기 + 곡별 "가사만 복사" 버튼**: 자막 결과 화면에서 실제 가사 블록에 들여쓰기(16px)와 넉넉한 세로 여백(20px)을 줘 파트가 눈에 띄게 구분되도록 했고, 곡마다 "이 곡 가사만 복사" 버튼을 추가해 마디 표기 없이 가사 줄만 클립보드로 복사할 수 있게 했다(기존 "전체 복사"는 연습용으로 마디 표기 포함해 그대로 유지).
- **여러 단어 구간 코드 자동 인식**: `Praise` 곡의 `Let Everything x2`처럼 공백으로 이어진 표기가 있으면 단어별로 쪼개져 미해결로 남는 문제를 사용자가 지적했다. 원문(송폼)은 팀원 전체가 보는 화면이라 절대 고치면 안 된다는 판단에 따라, **송폼 텍스트는 그대로 두고** 리더가 구간 코드를 원문 그대로("Let Everything") 등록하면 파서가 토큰화 이후 그 단어 수만큼 미리 묶어보도록 했다. 새 스키마·API·UI 없이 기존 자유 텍스트 구간 코드 입력만으로 동작한다.

**검증**: 8/23 콘티에 실제 등록된 데이터로 `lyrics_service.build_conti_lyrics`를 직접 호출해 조합 결과(구간 순서·줄 수)를 확인했고, 사용자가 실제로 자막팀에 전달했던 텍스트와 구조가 정확히 일치함을 확인했다. 별칭 매칭·코드-별칭 충돌 400·`last_song_form` 힌트·여러 단어 구간 코드 병합(더미 데이터로 "Let Everything x2 ... dummy phrase x2" 구조 재현, 송폼 원문 불변 확인)도 실 DB 테스트 계정으로 검증 후 정리했다.

**버그 발견 및 수정 — 미해결 토큰을 등록해도 계속 미해결로 남던 문제 (2026-08-21)**: 사용자가 Praise 곡의 `호흡있는`을 정확히 등록했는데도 자막 결과에 계속 미해결로 남는다고 제보했다. 원인은 파서(`classify_token`)가 `^[A-Za-z]로 시작`하는 형식만 `kind="section"`으로 분류하고, 한글 단어나 여러 글자 영단어는 애초에 `kind="unresolved"`로 분류돼 `lyrics_service`가 구간 조회 자체를 시도하지 않았던 것 — "미해결 표기를 원문 그대로 구간에 등록하면 다음부터 자동 해결된다"는 이 Phase의 핵심 전제가 정작 그 전제가 가장 필요한 케이스(한글·여러 글자 단어)에서는 동작하지 않던 버그였다. 그동안의 검증이 전부 `A`/`B`/`C` 같은 정형 코드로만 이뤄져 이 구멍을 놓쳤다.
`_build_song_blocks`의 최종 `unresolved` 분기에서도 원문 그대로 구간 목록을 한 번 더 조회하도록 수정했고, DB 없이 도는 순수 함수 단위 테스트 4건(`tests/test_lyrics_service.py`, 더미 데이터만 사용)을 추가했다. 실제 8/23 Praise 데이터로 재현·수정을 확인했다(`unresolved_count` 1 → 0).

**자막 가사 보기 ↔ 구간 편집 왕복 링크 (2026-08-21)**: `/conti/:id/lyrics`에서 곡마다 "가사 구간 편집" 링크를 추가하고(콘티 id를 쿼리로 함께 넘김), 미해결 표기의 "이 표기로 구간 등록" 링크도 동일하게 통일했다. `/songs/:id/sections`는 이 쿼리로 콘티 id가 들어오면 "이 콘티 자막 가사 보기" 링크를 노출해 원래 보던 콘티로 바로 돌아갈 수 있게 했다(콘티 id 없이 곡 관리 화면에서 바로 들어온 경우엔 표시 안 함). API·스키마 변경 없는 순수 프론트 네비게이션 추가.

#### 파생 결정 (SDD가 정하고 넘어간다 — 이견 있으면 알려주세요)

6. **신규 테이블은 구체적 FK 2개** — `notice_comments`(`notice_id` FK), `calendar_event_comments`(`event_id` FK). 이 프로젝트가 지금까지 범용 다형성 테이블(`commentable_type`+`commentable_id` 같은)을 쓴 적이 없고, 테이블 2개 늘어나는 비용보다 타입 안전성·단순한 FK 제약이 이득이 크다.
7. **작성자 이름은 작성 시점 스냅샷으로 저장** — `user_id`(uuid, `auth.users` 참조, `on delete set null`) + `author_name`(작성 시점 `display_name` 복사) 두 컬럼을 함께 둔다. 조회할 때마다 `user_profiles`를 조인하지 않아 구현이 단순하고, 탈퇴 계정(현재 앱엔 탈퇴 기능이 없지만 대비)의 과거 댓글도 이름이 사라지지 않는다. 이후 본인이 표시 이름을 바꿔도(Phase 7 후속 `/profile` 기능) 과거 댓글의 작성자 표기는 바뀌지 않는다 — 이 트레이드오프가 싫다면 매 조회 시 `user_profiles`를 조인하는 방식으로 바꿀 수 있다.
8. **"수정됨" 표시는 별도 컬럼 없이 `updated_at != created_at` 비교로 판단** — 신규 컬럼을 늘리지 않는다.
9. **수정 권한은 본인만, 삭제 권한은 본인 또는 `leader` 이상** — README 문구 그대로. 두 판정 모두 역할 게이트(`require_role`)만으로는 표현할 수 없어(리소스 소유권 비교가 필요) 서비스 레이어에서 `comment.user_id == current_user.id` 비교를 추가로 수행하고, 삭제만 `role >= leader`를 소유권 대신 허용한다. 라우터 의존성은 두 엔드포인트 모두 최소 `require_role("member")`로 걸고, 세부 판정은 그 안에서 403으로 처리한다.
10. **응답에 `can_edit`/`can_delete`를 서버가 계산해 포함** — 프론트가 "현재 로그인한 사용자 id/역할"과 "댓글 작성자 id"를 비교하는 로직을 중복 구현하지 않도록, Phase 6의 `match_status`처럼 서버가 미리 판정한 값을 내려준다.
11. **정렬은 작성순(오래된 것부터)** — 공지/캘린더처럼 최신순이 아니라 대화 흐름을 읽기 쉬운 순서를 택한다.
12. **신규 의존성 0개** — 기존 `require_role`, `auth.get_user` 패턴을 그대로 재사용한다.

#### 신설 테이블

```sql
create table notice_comments (
  id bigint generated always as identity primary key,
  notice_id bigint not null references notices(id) on delete cascade,
  user_id uuid references auth.users(id) on delete set null,
  author_name text not null,
  content text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table calendar_event_comments (
  id bigint generated always as identity primary key,
  event_id bigint not null references calendar_events(id) on delete cascade,
  user_id uuid references auth.users(id) on delete set null,
  author_name text not null,
  content text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

RLS는 다른 테이블과 동일하게 **활성화 + 정책 없음**(서버가 `service_role`로만 접근).

**문서 동기화**: API명세 2-4절(공지 댓글)·3-1절(캘린더 댓글) 신설, 0-1절에 댓글 인증 예외 명시, 5절 총계 49 → 57. ERD 엔티티 표(#16, #17) + mermaid + 3-9절 신설. `docs/schema.sql`에 두 테이블 DDL + `updated_at` 트리거 + RLS 반영.

#### Phase 10 후속 — 전체 점검(버그·보안·누락 기능) 및 수정 (2026-08-21)

Phase 10 완료 직후 사용자 요청으로 댓글 기능 전체를 다시 검토했다. "흔히 있는 기능인데 없는 것 / 보안 위험 /
버그" 세 갈래로 나눠 점검한 결과를 사용자에게 보고하고, 확인받은 항목만 반영했다.

**보안 점검 결과(문제 없음, 확인만 함)**: XSS(React가 텍스트 노드로 렌더링해 자동 이스케이프, `dangerouslySetInnerHTML` 미사용) · SQL 인젝션(Supabase 클라이언트가 전부 파라미터화된 쿼리 사용) · 작성자 위조(`author_name`은 요청 바디가 아니라 서버가 로그인 세션에서 채움) · CSRF(Bearer 토큰 기반이라 해당 없음).

**버그 4건 수정(사용자 확인 후 전부 반영)**:
1. **부모 ID 미검증** — `PATCH`/`DELETE`가 `comment_id`만으로 조회해, URL의 `notice_id`/`event_id`가 실제 소속과 달라도 조용히 성공했다(소유권 검사가 있어 권한 상승은 아니지만 REST 정합성 버그). `comment_repository.find_by_id`가 `select("*")`로 FK 컬럼까지 받아오도록 바꾸고, `comment_service._find_owned_comment`에서 `existing[fk_column] == parent_id`를 검증해 불일치 시 404로 막았다.
2. **`get_current_user_optional`의 좁은 예외 처리** — `except HTTPException`만 잡고 있어 Supabase 쪽 네트워크 순단(우리가 실제로 겪은 `httpx.ReadError [WinError 10035]`) 같은 예상 못한 예외가 그대로 튀어 올라 비로그인 GET 요청까지 500으로 깨졌다. "비로그인 조회는 절대 깨지면 안 된다"는 이 함수의 존재 이유를 지키도록 `except Exception`으로 넓혔다. 실제로 검증 중 겪었던 CORS처럼 보이는 간헐적 오류의 원인 중 하나로 추정된다.
3. **댓글 작성 시 부모 존재 확인 누락** — 존재하지 않는 `notice_id`/`event_id`로 댓글을 작성하면 FK 위반(23503)이 `main.py`의 전역 핸들러에서 처리되지 않는 코드라 500 + 원본 DB 에러 메시지가 노출됐다. 다른 서비스(`notice_service.get_notice` 등)처럼 라우터에서 부모 존재를 먼저 확인해 404로 막도록 추가했다.
4. **내용 미변경 시 "(수정됨)" 오탐** — `set_updated_at()` 트리거가 `UPDATE` 자체에 반응해 내용이 그대로여도 `updated_at`이 갱신됐다. `update_comment`가 기존 내용과 같으면 DB `UPDATE`를 건너뛰도록 no-op 가드를 추가했다(`update_display_name`의 기존 가드와 동일 패턴).

**기능 추가 4건(사용자가 선택)**:
- **내용 길이 제한**: 백엔드 `MAX_CONTENT_LENGTH=1000`(초과 시 400) + 프론트 `maxLength` 속성과 글자수 카운터(작성/수정 textarea 둘 다)
- **수정/삭제 더블클릭 방지 가드**: `CommentList.jsx`에 `savingEdit`/`deletingId` 상태 추가, 진행 중에는 버튼 비활성화(작성은 이미 `submitting`으로 막혀 있었음)
- **목록 화면 댓글 수 배지**: `GET /notices`·`GET /calendar` 응답에 `comment_count` 추가(곡 마스터의 `usage_count`와 동일한 중첩 집계 패턴, `notice_comments(count)`/`calendar_event_comments(count)`). 공지 목록(`NoticeMain.jsx`)에는 "💬 N" 텍스트로, 캘린더 그리드(`CalendarMain.jsx`)는 칸이 좁아 막대 텍스트 대신 `title` 툴팁에 표기
- **관리자의 댓글 삭제**: 확인 결과 `_LEADER_OR_ABOVE`에 이미 `admin`이 포함돼 있어 **기존 구현으로 충분**함을 확인, 별도 작업 없음

**검증**: `pytest`(기존 회귀 23건 + 신규 로직) + 실 DB 대상 직접 스크립트로 4건 버그 각각의 재현→수정 확인(부모 ID 불일치 404, 존재하지 않는 부모 404, 내용 미변경 시 `updated_at` 불변, 길이 초과 400) + `FastAPI TestClient`로 라우터 레벨 404 확인 + `comment_count`가 댓글 생성/삭제에 따라 실제로 바뀌는지 확인. `npm run build` 통과.

**트러블슈팅 — 유령 uvicorn 프로세스 다중 실행**: 백엔드 재시작 중 `taskkill //F //PID`(git-bash 경유)가 실제로는 프로세스를 죽이지 못했는데도 성공 메시지를 출력해, 이전 세션들의 uvicorn 프로세스 4개(`--reload`가 코드 변경을 계속 놓치는 원인)가 동시에 포트 8003에 남아있었다. `Get-CimInstance Win32_Process`(PowerShell)로 실제 커맨드라인을 확인해 4개 프로세스를 특정하고 `Stop-Process -Force`로 정리한 뒤에야 최신 코드가 반영됐다 — 이후에는 백엔드 재기동이 필요하면 PowerShell로 프로세스를 확인하는 편이 git-bash의 `taskkill`보다 신뢰도가 높다.

**문서 동기화**: API명세 2-4·3-1절(내용 길이 제한, 부모 검증, `comment_count` 필드 설명 추가).

##### 파생 결정 (SDD가 정하고 넘어간다)

6. **집계는 `monthly_schedules.year`/`month` 기준이지 `service_date` 기준이 아니다.** 스케줄 자체가 연·월 단위로 편성되고
   화면도 그 단위로 조회하므로, 주차의 실제 날짜가 달을 넘나드는 경계 케이스(예: `01-02` 주차)를 따로 처리할 필요가 없다.
7. **DB 왕복은 1회.** 그 해 전체의 마이크 배정 행을 한 번에 가져와 **월 집계와 연 집계를 파이썬에서 함께 계산**한다.
   22명 × 52주 × 마이크 8슬롯이면 연간 최대 400여 행이라 전송량이 문제되지 않는다.
8. **집계 함수는 순수 함수로 분리한다** (`aggregate_mic_counts(rows, month)`). Phase 9의 `song_form_parser`,
   Phase 10의 `comment_service.compute_permissions`와 같은 방식 — DB·네트워크 없이 도는 pytest를 붙일 수 있다.
9. **`member_id`가 없는 배정(`name_snapshot`만 있는 인물)은 집계에서 제외한다.** 인명부 밖 인물이라 애초에 드롭다운
   선택지에 없어 숫자를 붙일 자리가 없다(ERD 3-3). 제외한다는 사실을 SDD에 남겨, 나중에 "합계가 안 맞는다"는 오해를 막는다.
10. **조회 권한은 비로그인 공개(`require_role` 없음).** README 6절의 "조회는 전체 공개" 원칙을 그대로 따른다.
    실제로는 leader만 여는 편집 화면에서 쓰이지만, 배정 횟수는 이미 공개된 스케줄 데이터를 세어 만든 값이라
    Phase 9 가사처럼 좁혀야 할 이유가 없다.
11. **신규 의존성 0개, DB 스키마 변경 0건.** `schema.sql`·ERD는 손대지 않는다.

8. **확인 · 빌드 · 문서 동기화**
   실제 8~9월 데이터로 숫자가 스프레드시트 수작업 집계와 일치하는지 확인 → 배정 저장 후 숫자가 갱신되는지 →
   집계 API가 실패해도 폼이 살아있는지 → `pytest` 전체 통과 → `npm run build` 통과.
   **문서**: API명세 2-2절(엔드포인트 1개 추가)·5절 총계 57 → 58. README·ERD·`schema.sql`은 변경 없음(DB 스키마 무변경).

**진행 순서**: 1 → 2 → 3 → 5(집계 로직을 테스트로 먼저 굳힘) → 4 (백엔드 완결) → 6 → 7 → 8.

**되돌림 경계**: 기존 동작을 하나도 바꾸지 않는 **순수 추가**다(기존 코드 수정은 7번의 드롭다운 라벨뿐).
문제가 생기면 Phase 11-A 커밋 전체를 revert하면 Phase 10 상태로 그대로 돌아간다. DB 마이그레이션이 없어 되돌릴 스키마도 없다.

**남은 리스크**
1. **중첩 필터 쿼리(2번)가 기대대로 안 먹을 가능성** — 폴백을 미리 정해뒀으므로 막히지 않는다.
2. **과거 데이터가 없으면 숫자가 전부 0이라 당장은 쓸모가 없다.** 8~9월 실사용 데이터가 쌓여야 판단 근거가 된다 —
   이관해둔 과거 스케줄이 있으면 그만큼 바로 의미가 생긴다.
3. **마이크만 세므로 "콰이어로만 여러 번 나온 사람"은 0회로 보인다.** 사용자 확인을 거친 의도된 동작이지만,
   실사용에서 오해를 부르면 드롭다운 라벨에 "마이크 기준"임을 명시하는 것으로 보완한다.

**실제 진행 결과 (2026-08-22)**: 계획대로 1~8번 전부 구현·검증 완료. 계획과 달라진 점은 없었다.

- **리포지토리(2번)는 중첩 필터 시도 없이 처음부터 3단계 폴백 방식으로 구현**했다 — SDD가 "먼저 1회 조회를 시도하고
  안 되면 폴백"이라고 적어뒀지만, supabase-py 버전에 따른 불확실성을 검증하는 시간보다 처음부터 안전한 경로로
  가는 편이 이 규모(월 12건·주차 52건)에서 실질적으로 더 빨랐다. 3회 조회 비용 차이는 실측에서도 체감되지 않았다.
- **검증은 실제 Supabase 데이터로 진행**했다 — 임시 leader 테스트 계정을 만들어(가입 → `user_profile_repository.update_role`로
  즉시 승격) `/schedules/10/weeks/9/edit` 화면을 Playwright(임시 devDependency, `--no-save`로 설치)로 열어 마이크 1~8
  드롭다운에만 `이름 (이번 달 N회 · 올해 N회)` 형식이 붙고, 악기 7개·자막·콰이어·싱어 악보 드롭다운에는 붙지 않는 것을
  옵션 텍스트 덤프로 직접 확인했다. API 레벨에서도 2026년 8월(월 2회씩 8명)·9월(월 0회, 연 2회 유지)·데이터 없는
  2025년(빈 배열) 세 케이스를 curl로 확인했다.
- **트러블슈팅 — 죽은 프로세스가 포트를 계속 점유**: 이전 세션의 uvicorn/vite 프로세스를 `Stop-Process`로 종료했는데도
  `netstat`에는 여전히 `LISTENING`으로 남는 경우가 있었다(`Get-CimInstance`로 조회하면 해당 PID 자체가 이미 존재하지
  않음 — Windows 소켓 정리 지연으로 추정). Phase 1·6·10에서 겪은 유령 프로세스 문제의 새로운 변종이라, 이번에는
  강제 종료를 반복하는 대신 **다른 포트(8010)로 새로 띄우는 쪽으로 우회**했다. 검증 후 백엔드·프론트 프로세스와
  `.env.local`(8003 원복) 모두 정리했고, 만든 테스트 계정도 `supabase.auth.admin.delete_user`로 삭제했다.

#### Phase 11-B — 참/불참 텍스트 AI 파싱 (착수 예정, SDD 미작성)

### Phase 12 — 스케줄 배정 보조 · 싱어팀 자동 배정 제안 (착수 예정, 이 묶음의 마지막)
