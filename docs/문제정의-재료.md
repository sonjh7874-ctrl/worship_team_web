## 1. 주제 선정 경위 (왜 이 주제인가)

### 검토했던 후보
| 후보 | 결과 |
|---|---|
| ① 청운교회 청년부 주일찬양팀 콘티/인명부/공지 앱 | **채택** |
| ② 수업/회의 요약 및 todo list 정리 | 배제 |

### ②를 배제한 이유
- **차별점 확보 곤란**: Otter, Clova Note, Notion AI 등 이미 시장 포화. "요약+투두"만으로는 "그래서 뭐가 다른데?"에 답하기 어려움.
- **일정 리스크**: LLM 요약 *품질*을 쓸 만한 수준까지 끌어올리는 반복 튜닝이 필요. 코드 구조 문제가 아니라 "AI 아웃풋 품질" 문제라 10일 내 통제가 어려움.
- **실사용자 부재**: 본인 혼자 쓰는 수준에 머물 가능성이 높음.

### ①을 채택한 이유
- **차별점 +1이 스코프 자체에서 나옴**: 기존 교회 앱은 대부분 "교회 전체 관리"용 종합 솔루션(교인 명부·헌금·출석)으로 무겁고 비쌈. **찬양팀 콘티(곡 순서·키·파트 배정)에 특화된 가벼운 도구**는 시장에 거의 없음.
- **실사용자 확보**: 본인이 속한 팀에 바로 배포·피드백 가능 → "실제 N명이 쓰는 서비스"라는 포트폴리오 스토리.
- **일정 예측 가능성**: 도메인이 좁고 명확한 CRUD 중심이라 Vertical Slice를 빠르게 세울 수 있음.

### 사용자가 밝힌 포트폴리오 방향
> **"실사용자가 있는 실서비스 경험"** — 작더라도 실제로 쓰이는 서비스를 만들고 운영한 경험을 어필하고 싶음.

## 2. 타겟 페르소나

**청운교회 청년부 주일찬양팀 리더 (이무진, 97년생)** — 리더로서 매주 콘티를 받아 정리·배포하고, 월간 스케줄을 편성·공지하는 역할.

- 리더십 구성(2026): **리더**, 부리더, 싱어팀장, 악기팀장, 회계
- 팀 규모: **총 22명** (담당교역자 포함) — 싱어팀 13명, 악기팀 9명. 변동은 있으나 30명을 넘는 경우는 드물고 이 비율을 대체로 유지.
- 섬기는 예배: **4부예배만** 섬김 (주에 다른 콘티는 보통 없음)

### 왜 "리더십"이 페르소나인가
콘티·악보·스케줄 배포의 반복적 고통이 리더십에 집중되어 있고, 팀원들은 그 산출물을 "확인"하는 입장으로 자연스럽게 따라옴.

## 3. 문제 상황 (현재 워크플로우와 페인포인트)

### 3-1. 주간 콘티/송폼 흐름
1. **매주 수요일**, 목사님이 콘티(송폼)를 **카톡방에 이미지로** 올려주심.
2. 대부분 이전과 동일한 송폼이지만 **가끔 수정**됨.
3. 일반적으로 콘티 공지 **1~2일 후**, 악기팀이 악보를 만들어 별도로 공유.
4. 매주 **송폼까지 적힌 악보 PDF**로 제공됨.

**페인포인트**
- 익숙한 송폼이 바뀌면 어색해서 예배 중 **틀리는 경우**가 있음.
- 새 곡이라 송폼·곡 숙지가 안 되어 **예배 때 틀리거나 가사가 제대로 안 나오는** 경우.
- 카톡방에 대화가 쌓이면 **최신 콘티 이미지를 찾기 어려움**.
- 악보 공유가 **누락되거나 버전이 바뀌어** 혼선.
- **프린트된 종이 악보**를 따로 모아 싱어팀 연습에 쓰는데, 거기엔 **옛날 송폼이 남아있어** 연습 시 혼동.
- 자막팀에 넘길 "송폼대로 정리된 가사"를 **리더가 지금은 수작업**으로 만들고 있음.

### 3-2. 월간 스케줄 흐름
- 매 월말, 다음 달 섬김 일정(싱어팀/악기팀 나눠서)을 **구글 스프레드시트**에 편성.
- 정리 후 **이미지로 캡처해서 카톡방에 공지**.

**페인포인트**
- 원본(스프레드시트)과 공지본(캡처 이미지)이 **따로 놈** → 수정 시 불일치 위험.
- (신규 확인) 싱어팀은 단순 명단이 아니라 **마이크별 무대 위치가 고정**되어 있는데, 캡처 이미지만으로는 이 배치가 팀원에게 한눈에 전달되지 않고 표 안에 텍스트로만 나열됨.

### 3-3. 행사/일정 관리
- 교회 행사나 찬양팀 내 행사를 정리해두는 공간이 없어 **기억에 의존**하거나 보통 1달 전에 즉흥적으로 준비.

### 3-4. 문제의 공통 원인 (한 줄 요약)
> **"최신 버전이 어디 있는지, 그게 최신인지 아닌지를 확신할 수 있는 단일한 곳이 없다."**
> 카톡방은 대화에 묻히고, 종이 악보는 업데이트가 안 되고, 스프레드시트는 캡처 이미지로만 공지되어 원본과 분리됨.

### 3-5. 심각도에 대한 사용자 진술 (과장 금지)
> "어떻게든 잘 대처해서 **크게 문제가 터진 적은 아직 없음**. 다만 소소한 문제는 많았음."
→ 문제정의서 작성 시 이 톤을 유지할 것. "대형 사고" 프레이밍은 사실과 다름.

## 5. MVP 핵심 기능 3개

> **중요**: 세 문제(콘티/공지/캘린더)는 **성격이 달라서 하나의 기능으로 묶지 않고 각각 별도 기능으로 구현**한다. (사용자가 명시적으로 지시)

### 기능 1 — 이번 주 콘티/송폼

**목적**: 팀원이 **이 화면 하나만 보고 연습**할 수 있게 한다. 콘티·송폼·곡 정보·악보를 한 곳에.

**데이터 단위**
- 콘티 1건 = **날짜 + 제목**
- 제목 기본값 `"주일예배"`, 자유롭게 수정 가능 (예: `"수련회 1일차 저녁집회"`)
- **이유**: 평소엔 4부예배 콘티 주 1건뿐이지만, 수련회·특별새벽집회 등 예외적으로 콘티가 여러 개 필요한 기간이 있음. 요일/주차에 고정하지 않고 날짜+제목 단위로 두면 예외 처리 로직 없이 두 케이스를 모두 커버.
- 화면에는 "가장 최근/다가오는 콘티"를 메인에 표시.

**곡 데이터 구조 — "반(半)구조화" 방식**
| 항목 | 저장 방식 | 이유 |
|---|---|---|
| 곡 제목 | 구조화 필드 | 깔끔하게 떨어짐 |
| 아티스트 | 구조화 필드 | 깔끔하게 떨어짐 |
| 키(Key) | 구조화 필드 | 깔끔하게 떨어짐 |
| **송폼** | **자유 텍스트 한 덩어리** | 표기가 곡마다 불규칙(A1/B/(맞4)/(up)/bis/Tag/x2). 고정 필드 틀에 억지로 끼우면 예외 처리에 시간을 더 뺏김 |

**AI 콘티 인식 (차별점 +1의 핵심)**
- 콘티 **이미지를 비전 지원 LLM API**(Claude / GPT 등)에 전달 → "곡 순서·제목·키·송폼을 JSON으로 추출" 프롬프트 → **별도 OCR 라이브러리 없이 1회 API 호출로 인식+구조화 동시 처리**.
- 이미지가 인쇄 텍스트라 화질·구조가 깔끔해 인식 난이도 낮음.
- **정확도 기대치**: 제목/키는 신뢰도 높음. 송폼 약어는 "이해·재구성"이 아니라 **원문 그대로 옮기는 수준**으로 기대. 곡명 표기가 애매한 경우(축약 팀명, 특수문자) 가끔 틀릴 수 있음.
- **사람 검수 단계는 필수** — 리더십이 AI 추출 결과를 확인·수정한 뒤 게시하는 화면을 반드시 둔다.

**악보**
- PDF 업로드. **업로드 권한은 리더십만** (MVP 확정).
- 추후 테스트 중 악기팀원 직접 업로드 필요성이 확인되면 악보 수정 권한만 별도로 분리 가능하도록 여지를 남긴다. (시간 부족으로 MVP에서는 안 함)

**UI 구조**
- 메인: 최신 콘티 1건 상세
- 하단: 과거 콘티 목록(제목·날짜만 간단히)
- 목록 클릭 → **상세 페이지로 이동** (`/conti/12` 형태)
- **모달/팝업 대신 페이지 이동을 선택한 이유**: ①메인의 상세 화면 컴포넌트를 그대로 재사용 가능해 개발량 감소 ②모바일에서 팝업 안에 PDF·이미지·텍스트를 넣으면 답답함 ③모달 상태 관리(열림/닫힘·뒤로가기)가 번거로움 ④페이지 이동은 모바일 뒤로가기와 자연스럽게 맞물림

**2단계 확장 기능 (MVP 이후, 8/20~26 중 여유 시)** — *자막용 가사 자동 정리*
- **배경**: 자막팀에 넘길 "송폼 순서대로 정리된 가사"를 현재 리더가 수작업으로 만듦. 자동화 시 리더 시간 단축 + 일반 팀원 연습에도 도움.
- **설계 (2단계 분리가 핵심)**:
  1. **곡 고유 속성**: 그 곡 가사의 어디까지가 A(벌스), B(코러스), C… 인지 매핑 → 한 번 정해두면 **다음에 같은 곡이 나올 때 재사용**(DB 누적)
  2. **주간 가변 속성**: 이번 주 송폼 순서 (예: `A1 A2 B (맞4) A2 B …`)
  3. **최종 조합**: 송폼 순서대로 1번의 구간 가사를 이어 붙이면 자막용 가사 완성 → **이 단계는 AI 불필요, 단순 로직이라 안정적**
- **가사 원문 확보 방식**: CCM 가사는 **저작권 문제로 안정적인 무료 API가 없음** → 자동 검색은 배제. **사람이 가사를 붙여넣고, AI는 A/B/C 구간 구분만 제안, 사람이 검수·확정**.
- **우선순위**: 콘티 기본 CRUD가 확실히 동작한 뒤에 얹는다. 시간 부족 시 포기해도 프로젝트가 무너지지 않도록.

### 기능 2 — 공지사항 (월간 스케줄 포함)

**목적**: 여러 채널에 흩어지던 찬양팀 공지를 한 곳에. **월간 스케줄을 상단 고정**으로 중요 포지션에 배치.

**스케줄 데이터**
- **저장**: 월 단위로 **계속 누적** (1년치든 그 이상이든 DB에는 쌓임)
- **조회**: 화면에서는 **해당 월만** 표시. 1년치를 한 화면에 보는 기능은 시간상 어렵고 꼭 필요하지도 않음(사용자 판단).
- **포지션 필드 = 고정** (앞으로 늘어날 가능성 거의 없음):
  - 악기팀: `Key1`, `Key2`, `드럼`, `베이스`, `일렉`, `싱도(싱어팀 도우미)/자막`, `악보`(1명)
  - 싱어팀: **마이크 1~8번 슬롯 + 콰이어 목록** (아래 5-1 참조), `자막`, `악보`(보통 2명이 나눠 맡음, 다중 선택)
  - 공통: `불참사항` (**표시함**), `특순`
- **빈 값 처리**: 기입된 값이 없는 항목은 **웹 화면에 표시하지 않음**
- **인덕션 시트**: MVP 제외 (예비용)

#### 5-1. 싱어팀 마이크 배치 시각화 (신규 확정 요구사항)

**배경**: 싱어팀은 단순 명단이 아니라 **무대 위 고정된 마이크 위치(1~8번)** 에 매주 다른 사람이 배정되는 구조. 지금은 캡처 이미지 표에 2줄로 텍스트 나열되어 있어 직관적으로 "누가 어디 서는지"가 전달되지 않음. 팀원이 실제 무대 위치를 한눈에 알 수 있도록 **시각적으로 배치도 형태**로 보여줘야 함.

**데이터 구조**
```
싱어_주간배정 = {
  mic1 ~ mic8: 팀원 | null,   // 8개 고정 슬롯, 비어있으면 미표시
  콰이어: [팀원, ...]          // 마이크 미배정 인원
}
```
- 마이크 슬롯은 **8개로 고정**(마이크 개수·무대 구조 자체가 바뀌지 않는 한 늘어나지 않음).
- 값이 없는 마이크 슬롯은 화면에 표시하지 않음(기존 "빈 값 숨김" 원칙과 동일).

**시각화 방식**
- 무대 배치(좌표) 자체는 **고정**이므로 코드에 하드코딩: 앞줄(4·3·[목사님 자리]·2·1) / 뒷줄(8·7·[여백]·6·5) 2단 그리드로 배치.
- 매주 바뀌는 것은 **각 슬롯에 채워지는 이름뿐** → CSS Grid + 고정 좌표 컴포넌트로 구현하면 추가 로직 없이 매주 데이터만 갈아 끼우면 됨.
- 상단에 "회중석" 라벨, 하단에 "콰이어: 이름1, 이름2" 텍스트를 붙여 실제 배치도와 동일한 느낌으로 표현.

**입력 UI**
- 리더십이 스케줄 입력 시 마이크 1~8번 슬롯마다 인명부 기반 드롭다운(팀원 선택) 8개 + 콰이어 인원 다중 선택 1개.

**구현 난이도 평가**: 무대 좌표가 고정값이라 "고정 도면 위에 동적 텍스트를 얹는" 정도로, 기본 CRUD 대비 추가 공수가 크지 않음. 다만 시각적 컴포넌트(그리드 레이아웃)가 하나 더 필요하므로, **기능 2의 기본 CRUD(글 등록/조회)가 먼저 동작한 뒤 배치도 시각화를 얹는 순서**로 진행.

### 기능 3 — 캘린더

**목적**: 전체 인원이 비정기 행사를 확인할 수 있는 공간. 기억에 의존하거나 1달 전 즉흥 준비하던 문제 해소.

**역할 분담 원칙 (겹침 방지)**
- **정기 주일예배 안에서 일어나는 것**(특순 포함) → **공지사항/스케줄**이 관장
- **정기 주일예배 밖의 비정기 행사**(수련회, 엠티, 며칠씩 걸리는 행사) → **캘린더**가 관장

**이벤트 구성**
- 제목, 날짜
- **카테고리 드롭다운**: 수련회 / 엠티 / 특순 등 **대표값은 고정**, 그 외는 `기타` 또는 직접 입력으로 추가
- **참여 인원** (리더십이 확정 인원 입력)
- **자유 텍스트 메모** (준비물, 장소 등 추가 내용)

**투표 기능은 제외**
- 구현 시간이 오래 걸림. 투표는 **기존대로 카톡에서 마무리**하고, 리더십이 **확정된 인원만** 캘린더에 입력.

**특순 연동 (사용자 아이디어 — 채택)**
- 캘린더 카테고리가 `특순`인 경우, **공지사항이 원본(source of truth)**.
- 공지사항에 특순 정보(날짜 + 인원)를 입력하면 → 캘린더에 자동 반영.
- **반드시 한 방향 동기화**: 캘린더에서 특순 항목을 직접 수정하면 안 됨. 수정하려면 공지사항에서 고쳐야 캘린더에 반영.
  - **이유**: 양방향이면 두 곳의 값이 어긋나는, 애초에 이 프로젝트가 없애려는 문제가 재발함.
- 구현: 공지사항의 특순 필드 저장 시 서버가 캘린더에 "자동 생성됨" 표시가 붙은 이벤트를 생성. 필드가 비면 해당 이벤트 삭제/숨김.
- 수련회·엠티 등 공지사항에 원본 데이터가 없는 이벤트는 캘린더에서 직접 자유롭게 등록·수정.
- **구현 우선순위**: 기본 CRUD 3종이 각각 독립적으로 잘 동작한 **뒤에** 얹는 동기화 로직. 일정이 빠듯해져도 세 기능이 독립적으로 완성된 상태는 확보할 것.

## 6. 공통 데이터 — 인명부

- **별도 "핵심 기능"으로 세지 않음.** 스케줄 배정 시 드롭다운용 마스터 데이터 성격(마이크 슬롯 배정, 악기 포지션 배정 등에 모두 사용).
- **MVP 필드 (최소화)**: `이름`, `팀구분(싱어/악기)`, `활동 여부(재직/탈퇴)`
- **제외한 필드와 이유**: 회비상태(O/X), 티셔츠 사이즈, 생일, 겸직 여부, 입부일, 또래(연생), 탈퇴 사유 등 — 핵심 기능 3개 어디에도 직접 쓰이지 않는 운영 정보. 연락처는 개인정보라 필수 아님.
- **변동 대응**: 인원 변동이 계속 있으므로 **고정값이 아니라 편집 가능**해야 함.
- **편집 권한**: **리더십만** 추가/수정/삭제 가능.

## 8. 기술 스택 및 선정 근거

### 확정: **FastAPI (Python) + React (반응형 웹) + Supabase (PostgreSQL)**

### 백엔드 — FastAPI 선택 이유
| 기준 | FastAPI | Spring Boot |
|---|---|---|
| 코드량/학습곡선 | 적음, 파이썬 문법 | boilerplate 많음, 개념 학습 시간 필요 |
| 10일 일정 적합성 | CRUD 빠르게 구현 | 셋업·구조 잡는 데 시간 더 소요 |
| AI/비전 API 연동 | **파이썬 생태계가 압도적 유리** (대부분 AI SDK가 파이썬 우선) | 가능하나 라이브러리 지원 적음 |
| Swagger 문서화 | **자동 생성** — 산출물 요구사항인 API 명세서와 직결 | SpringDoc 등 별도 설정 |
| 적합 상황 | 소규모/솔로, 빠른 MVP, AI 기능 | 대규모 트래픽, 복잡한 비즈니스 로직 |

→ 혼자 10일, AI 콘티 파싱이 핵심 기능이므로 FastAPI.

### 프론트 — React(웹) 선택 이유 (vs Flutter 앱)
| 기준 | React(웹) | Flutter(앱) |
|---|---|---|
| 배포 | **링크 공유만으로 즉시 접속** | 스토어 등록(심사) 또는 APK 직접 배포·TestFlight |
| 테스트 멤버 배포 | 카톡에 링크만 | 개인별 설치 지원 필요, 손이 많이 감 |
| 10일 일정 | 웹 하나만 | iOS/안드로이드 둘 다 신경 |
| 푸시 알림 | 브라우저 푸시는 제약 많음 | 네이티브 푸시 쉬움 |
| 오프라인 | 기본 인터넷 필요 | 캐싱 자연스러움 |
| UX/성능 | 웹 수준(콘티/공지/캘린더는 텍스트·표·이미지 위주라 충분) | 네이티브 수준 |

→ **결정적 논리**: Flutter의 핵심 장점(푸시 알림, 스토어 설치 경험)이 우리가 **이미 스킵하기로 한 항목들**과 정확히 겹침. 실제로 필요한 건 "링크 하나로 빠르게 접속"뿐. 사용자도 "모바일로 대부분 사용하지만 iOS/안드로이드 고려사항이 많아 우선 웹" 판단.
→ 단, **모바일 우선 반응형**으로 설계할 것 (실사용의 대부분이 모바일).
→ Flutter는 사용자가 간단히 배운 경험이 있으나, 이번 프로젝트의 차별점은 "AI 콘티 인식 + 실사용자 피드백"이지 "네이티브 앱 여부"가 아니므로 배제.

### DB — Supabase 선택 이유
| 기준 | PostgreSQL 단독 | **Supabase** | Firebase | Oracle |
|---|---|---|---|---|
| 데이터 적합성 | 관계형, 적합 | **PostgreSQL 기반, 적합** | NoSQL — 표 형태에 부자연스러움 | 관계형이나 과함 |
| 셋업 속도 | 직접 구축·운영 | **가입만 하면 관리형 DB + 대시보드** | 빠름 | 무겁고 복잡 |
| 파일 저장(콘티 이미지/악보 PDF) | 별도 스토리지 필요 | **Storage 내장** | 내장 | 별도 구성 |
| 로그인 확장 여지 | 직접 구현 | **Auth 내장 — 나중에 붙이기 쉬움** | 내장 | 무거움 |
| 비용/규모 | 무료지만 운영 부담 | **무료 티어로 충분** | 소규모 충분 | 22명 규모에 과잉 |

→ 스케줄이라는 관계형 데이터, 파일 업로드 필요, 추후 로그인 확장 여지, SQL을 깊게 모르는 상태에서 **대시보드로 데이터를 눈으로 확인**하고 싶은 니즈까지 종합 → Supabase.

## 11. 구현 우선순위 (일정 리스크 관리)

1. **1순위 — 기본 CRUD 3종 각각 독립 동작**
   콘티 등록→조회, 공지사항 등록→조회, 캘린더 등록→조회. Vertical Slice(화면→API→저장→조회) 우선, 디자인은 나중.
2. **2순위 — 수정 비밀번호 게이트 + 인명부 편집**
   여기까지가 "반드시 완성하는 최소 기준".
3. **3순위 — AI 콘티 이미지 인식 + 사람 검수 화면** (차별점 +1의 핵심)
4. **4순위 — 싱어팀 마이크 배치도 시각화** (공지사항 기본 CRUD 위에 얹는 컴포넌트)
5. **5순위 — 특순 공지사항↔캘린더 한 방향 동기화**
6. **6순위 — 자막용 가사 자동 정리** (곡 섹션 매핑 누적 + 송폼 순서 조합)
7. **정식 로그인/리더십 역할 구분** — 원래 "여유 시" 항목이었으나 2026-08-20 정식 구현으로 확정, AI 콘티 이미지 인식(3순위) 이후 착수

## 13. 협업 시 유의사항 (다음 세션용 메모)

- 사용자는 **한 단계씩 천천히** 진행하는 것을 선호. 답변 하나 받았다고 바로 산출물(문제정의서 등)을 만들지 말 것. **사용자가 "이제 만들자"고 할 때까지 재료만 쌓을 것.**
- 사용자는 각 기술 선택의 **근거와 장단점 비교**를 원함. 기본 지식은 있으나 깊게는 모르는 상태.
- MVP 원칙: 핵심 기능 3개 초과 금지. 새 기능 제안 시 "이게 핵심 3개 안에 드는가?" 먼저 점검.
- **용어 주의**: "싱도"는 신디사이저가 아니라 **"싱어팀 도우미"** 를 뜻함(사용자가 직접 정정). 악기팀 컬럼에 있지만 실제로는 사람 역할.
- **개인정보 처리**: 사용자가 문서상 리더십 이름을 실명 대신 예시명("이무진" 등)으로 바꿔둔 것으로 보임 — 향후 문서 작성 시 이 기준(익명화 여부)을 사용자에게 재확인할 것.
