# 청운교회 청년부 주일찬양팀 웹 (가칭)

> 매주 흩어지는 콘티·악보·섬김 일정을 한 곳에 모으는, 찬양팀 전용 경량 웹 서비스
>
> LG DX SCHOOL 바이브코딩 개인 사이드 프로젝트 (2026.08.17 ~ 08.28, 10일)

---

## 1. 문제 정의

### 1-1. 현재 워크플로우

**주간 콘티/송폼**

1. 매주 수요일, 목사님이 콘티(송폼)를 **카톡방에 이미지로** 공유
2. 대부분 이전과 동일한 송폼이지만 가끔 수정됨
3. 콘티 공지 1~2일 후, 악기팀이 **송폼까지 적힌 악보 PDF**를 별도로 공유

**월간 스케줄**

1. 매 월말, 다음 달 섬김 일정(싱어팀/악기팀)을 **구글 스프레드시트**에 편성
2. 정리 후 **이미지로 캡처해 카톡방에 공지**

**행사 일정**

- 교회 행사·찬양팀 행사를 정리해두는 공간이 없어, 기억에 의존하거나 보통 1달 전에 즉흥적으로 준비

### 1-2. 페인포인트

| 구분 | 문제 |
|---|---|
| 콘티 | 익숙한 송폼이 바뀌면 어색해 예배 중 틀리는 경우가 있음 |
| 콘티 | 새 곡이라 송폼·곡 숙지가 안 되어 예배 때 틀리거나 가사가 제대로 나오지 않음 |
| 콘티 | 카톡방에 대화가 쌓이면 최신 콘티 이미지를 찾기 어려움 |
| 악보 | 악보 공유가 누락되거나 버전이 바뀌어 혼선 |
| 악보 | 싱어팀 연습에 쓰는 프린트된 종이 악보에 **옛날 송폼이 남아 있어** 혼동 |
| 콘티 | 자막팀에 넘길 "송폼대로 정리된 가사"를 리더가 매주 수작업으로 제작 |
| 스케줄 | 원본(스프레드시트)과 공지본(캡처 이미지)이 분리되어 수정 시 불일치 위험 |
| 스케줄 | 싱어팀은 **마이크별 무대 위치가 고정**되어 있으나, 캡처 이미지의 표 텍스트만으로는 배치가 한눈에 전달되지 않음 |
| 행사 | 비정기 행사를 확인할 공간이 없어 준비가 즉흥적임 |

### 1-3. 문제의 공통 원인

> **"최신 버전이 어디 있는지, 그리고 그것이 정말 최신인지를 확신할 수 있는 단일한 장소가 없다."**

카톡방은 대화에 묻히고, 종이 악보는 업데이트되지 않으며, 스프레드시트는 캡처 이미지로만 공지되어 원본과 분리된다.

### 1-4. 문제의 심각도 (사실 그대로)

지금까지 **큰 사고가 발생한 적은 없다.** 팀이 그때그때 잘 대처해왔다. 다만 위와 같은 소소한 마찰이 매주 반복되고 있으며, 이 서비스는 그 반복적인 마찰을 줄이는 것을 목표로 한다. 과장된 위기 상황을 전제로 하지 않는다.

## 2. 타겟 사용자

### 핵심 페르소나 — 주일찬양팀 리더 (가명: 이무진, 97년생)

매주 콘티를 받아 정리·배포하고, 월간 섬김 일정을 편성·공지하는 역할.

- **팀 구성**: 총 22명 (담당교역자 포함) — 싱어팀 13명, 악기팀 9명
- **리더십**: 리더, 부리더, 싱어팀장, 악기팀장, 회계
- **섬기는 예배**: 4부예배 (주에 다른 콘티는 보통 없음)

### 왜 리더십이 페르소나인가

콘티·악보·스케줄 배포의 반복적 고통이 리더십에 집중되어 있다. 일반 팀원은 그 산출물을 "확인"하는 입장이므로, 리더십의 문제를 해결하면 팀원의 사용 흐름은 자연스럽게 따라온다.

## 3. 왜 이 문제인가

### 차별점 +1이 스코프 자체에서 나온다

기존 교회 관련 서비스는 대부분 **교회 전체 관리용 종합 솔루션**(교인 명부·헌금·출석)으로 무겁고 비싸다. **찬양팀 콘티(곡 순서·키·파트 배정)에 특화된 가벼운 도구**는 시장에서 찾기 어렵다.

여기에 **콘티 이미지를 비전 LLM으로 자동 구조화**하는 기능을 얹어, "이미지를 수동으로 옮겨 적는" 작업 자체를 없애는 것이 이 프로젝트의 핵심 차별점이다.

### 실사용자를 즉시 확보할 수 있다

본인이 속한 팀에 바로 배포하고 피드백을 받을 수 있다. **"실사용자가 있는 실서비스를 만들고 운영한 경험"** 이 이 프로젝트의 포트폴리오 방향이다.

### 10일 안에 완성 가능하다

도메인이 좁고 명확한 CRUD 중심이라, Vertical Slice(화면→API→저장→조회)를 빠르게 세울 수 있고 일정 예측이 가능하다.

## 4. MVP 범위

> **원칙**: 핵심 사용자 1명, 핵심 기능 3개를 넘지 않는다. 기능이 많은 것보다 **작아도 실제로 동작하는 완성본**을 우선한다.

세 문제(콘티 / 공지·스케줄 / 캘린더)는 성격이 다르므로 하나로 묶지 않고 **각각 독립된 기능으로 구현**한다.

### 기능 1 — 이번 주 콘티/송폼

**목적**: 팀원이 이 화면 하나만 보고 연습할 수 있게 한다.

- **데이터 단위**: 콘티 1건 = `날짜 + 제목`
  - 제목 기본값은 `"주일예배"`, 자유 수정 가능 (예: `"수련회 1일차 저녁집회"`)
  - 요일/주차에 고정하지 않고 날짜+제목 단위로 두면, 평소의 주 1건과 수련회·특새 기간의 다건을 **예외 처리 로직 없이 모두 커버**한다.
- **곡 데이터 — 반(半)구조화 방식**

  | 항목 | 저장 방식 | 이유 |
  |---|---|---|
  | 곡 제목 / 아티스트 / 키 | 구조화 필드 | 값이 깔끔하게 떨어짐 |
  | 송폼 | **자유 텍스트 한 덩어리** | 표기가 곡마다 불규칙(`A1`/`B`/`(맞4)`/`(up)`/`bis`/`Tag`/`x2`). 고정 필드에 억지로 끼우면 예외 처리에 시간을 더 뺏김 |

- **AI 콘티 인식**: 콘티 이미지를 비전 지원 LLM API에 전달 → "곡 순서·제목·키·송폼을 JSON으로 추출" → 별도 OCR 라이브러리 없이 **1회 API 호출로 인식과 구조화를 동시 처리**
  - 원본이 인쇄 텍스트 이미지라 인식 난이도가 낮다.
  - 기대치: 제목·키는 신뢰도가 높고, 송폼 약어는 "이해·재구성"이 아니라 **원문 그대로 옮기는 수준**으로 기대한다.
  - **실측(2026-08-20)**: 실제 콘티 이미지 5장(곡 27건)으로 필드 단위 **94.8%** — 날짜 5/5, 제목 96%, 아티스트 96%, 키·note 100%, 송폼 81~85%. 정확도를 높인 방법과 한계는 `전체_로드맵.md`의 "Phase 6 후속" 절 참고.
  - **사람 검수 단계는 필수** — 리더십이 추출 결과를 확인·수정한 뒤 게시한다. 검수 화면은 곡 검색, 유사 곡 후보 제안(자모 유사도), 지난번 송폼과의 차이 강조로 남은 오류를 사람이 잡도록 돕는다.
- **악보**: PDF 업로드, **업로드 권한은 리더십만**
- **UI**: 콘티 화면(`/conti`)에 최신 콘티 1건 상세, 하단에 과거 콘티 목록 → 클릭 시 **상세 페이지 이동**(`/conti/12`)
  - 모달이 아닌 페이지 이동을 택한 이유: ① 콘티 화면의 상세 컴포넌트를 그대로 재사용해 개발량 감소 ② 모바일에서 팝업 안에 PDF·이미지·텍스트를 넣으면 답답함 ③ 모달 상태 관리(열림/닫힘·뒤로가기)가 번거로움 ④ 페이지 이동이 모바일 뒤로가기와 자연스럽게 맞물림
  - 사이트 루트(`/`)는 별도 대시보드가 차지한다(콘티/스케줄/공지 요약을 한 화면에서 보여주는 관문 페이지). 초기엔 루트가 콘티 화면이었으나, 기능 2까지 갖춰진 뒤 대시보드로 교체했다 — 자세한 배경은 `전체_로드맵.md` Phase 3 참고.

### 기능 2 — 공지사항 (월간 스케줄 포함)

**목적**: 여러 채널에 흩어지던 공지를 한 곳에 모으고, 월간 스케줄을 상단 고정으로 배치한다.

- **저장**: 월 단위로 계속 누적 / **조회**: 화면에는 해당 월만 표시
- **포지션 필드 (고정)**
  - 악기팀: `Key1`, `Key2`, `드럼`, `베이스`, `일렉`, `싱도(싱어팀 도우미)/자막`, `악보`(1명)
  - 싱어팀: **마이크 1~8번 슬롯 + 콰이어 목록**, `자막`, `악보`(보통 2명이 나눠 맡음, 다중 선택)
  - 공통: `불참사항`, `특순`
- **빈 값 처리**: 기입되지 않은 항목은 화면에 표시하지 않는다.

#### 싱어팀 마이크 배치 시각화

싱어팀은 단순 명단이 아니라 **무대 위 고정된 마이크 위치(1~8번)** 에 매주 다른 사람이 배정되는 구조다. 현재는 캡처 이미지 표에 2줄 텍스트로 나열되어 "누가 어디에 서는지"가 직관적으로 전달되지 않는다.

```
        (회중석)
   4   3   목사님   2   1      ← 앞줄
   8   7           6   5      ← 뒷줄
        (콰이어)
```

- 무대 배치(좌표)는 **매주 고정**이므로 코드에 하드코딩하고, 매주 바뀌는 것은 **각 슬롯에 채워지는 이름뿐**이다.
- CSS Grid 기반 고정 좌표 컴포넌트로 구현하면 추가 로직 없이 데이터만 교체하면 된다.
- 값이 없는 마이크 슬롯은 표시하지 않는다 (빈 값 숨김 원칙과 동일).
- **입력 UI**: 마이크 1~8번 슬롯마다 인명부 기반 드롭다운 + 콰이어 다중 선택

> 예시 (가명):
> 앞줄 — 4: 최나린 / 3: 서다은 / 2: 임하늘 / 1: 정승주
> 뒷줄 — 8: 한도윤 / 7: 오세진 / 6: 윤소미 / 5: 배현우
> 콰이어 — 노유안, 류지원

#### 공지 게시판

- 스케줄 외 일반 찬양팀 공지도 함께 게시
- 작성/수정은 리더십만, UI는 콘티와 동일 패턴(메인 최신 + 하단 목록 → 상세 페이지)

### 기능 3 — 캘린더

**목적**: 전체 인원이 비정기 행사를 확인할 수 있는 공간. 기억에 의존하거나 즉흥적으로 준비하던 문제를 해소한다.

- **역할 분담 (겹침 방지)**
  - 정기 주일예배 **안에서** 일어나는 것(특순 포함) → **공지사항/스케줄**이 관장
  - 정기 주일예배 **밖의** 비정기 행사(수련회, 엠티 등) → **캘린더**가 관장
- **이벤트 구성**: 제목, 날짜, 카테고리(수련회/엠티/특순 등 대표값 고정 + 기타), 참여 인원, 자유 메모
- **특순 연동**: 카테고리가 `특순`인 경우 **공지사항이 원본(source of truth)** 이며 **한 방향으로만 동기화**한다. 캘린더에서 직접 수정할 수 없고, 수정하려면 공지사항에서 고쳐야 한다.
  - 양방향으로 두면 두 곳의 값이 어긋나는, **애초에 이 프로젝트가 없애려는 문제가 재발**하기 때문이다.

### 공통 데이터 — 인명부

핵심 기능으로 세지 않는다. 스케줄 배정 시 드롭다운용 마스터 데이터 성격이다.

- **필드 (최소화)**: `이름`, `팀구분(싱어/악기)`, `활동 여부`
- **제외 필드**: 회비 상태, 티셔츠 사이즈, 생일, 겸직, 입부일, 연락처 등 — 핵심 기능 어디에도 쓰이지 않는 운영 정보이며, 연락처는 개인정보라 보관하지 않는다.
- 인원 변동이 잦으므로 **편집 가능**해야 하며, 편집 권한은 리더십만 갖는다.

## 5. 확장 범위 (MVP 이후, 여유 시)

> 아래는 **MVP 완성 기준에 포함되지 않는다.** 핵심 기능 3개가 확실히 동작한 뒤에만 착수하며, 포기해도 프로젝트가 성립한다.

### 자막용 가사 자동 정리 — ✅ 완료 (Phase 9, 2026-08-21)

리더가 매주 수작업으로 만드는 "송폼 순서대로 정리된 가사"를 자동화했다.

1. **곡 고유 속성**: 그 곡 가사의 어디까지가 A(벌스), B(코러스), C…인지 매핑(`song_sections`) → 한 번 정해두면 **다음에 같은 곡이 나올 때 재사용**(DB 누적)
2. **주간 가변 속성**: 이번 주 송폼 순서(`conti_songs.song_form`, 이미 저장돼 있던 값을 그대로 재사용)
3. **조합**: 송폼 순서대로 구간 가사를 이어 붙이면 완성 → 이 단계는 **AI 불필요, 단순 로직이라 안정적**. 실제 송폼 27건(토큰 336개) 분석으로 문법을 확정하고, 조합 결과는 저장하지 않고 매 요청 계산한다

가사 원문은 저작권 문제로 안정적인 무료 API가 없어 자동 검색을 배제했다. **사람이 가사를 붙여넣고(`/songs/:id/sections`), AI는 이번 단계에 관여하지 않으며, 구간 구분 제안은 후속 과제로 남겨뒀다.** 저작권 있는 콘텐츠라 가사 관련 조회(`/songs/:id/sections`, `/conti/:id/lyrics`)만 로그인(member 이상)을 요구한다 — 다른 조회는 그대로 비로그인 공개 유지. 송폼 해석에 실패한 표기는 에러 없이 `[?]` 표시로 남기고 사람이 그 자리에서 구간을 등록하면 다음부터 자동 해결된다. 상세 설계와 실제 진행 결과는 `전체_로드맵.md` Phase 9 절 참고.

### 정식 로그인 / 리더십 역할 구분 — ✅ 완료 (Phase 7, 2026-08-20)

원래는 "시간이 허락하면" 여유 항목이었으나, 일정에 여유가 생겨 **정식으로 구현하기로 확정**했고(2026-08-20), 같은 날 완료했다. Supabase Auth(이메일+비밀번호) 로그인 + admin/leader/member 3단계 역할로 기존 `EDIT_PASSWORD` 게이트를 **완전히 대체**했다. 상세 설계와 실제 진행 결과는 `전체_로드맵.md` Phase 7 절 참고.

### 댓글 기능 — 착수 확정 (Phase 10)

## 6. 권한 / 접근 정책

| 항목 | 결정 |
|---|---|
| 로그인 | **Supabase Auth(이메일+비밀번호)**, 앱 내 회원가입 가능 (Phase 7, 2026-08-20 완료) |
| 사이트 접근 | 조회(GET)는 **비로그인 상태에서도 전체 공개** — 초대 링크(URL)만 알면 누구나 볼 수 있는 정책은 로그인 도입 후에도 유지 |
| 역할 | **admin(관리자) / leader(리더십) / member(팀원)** 3단계. 가입 직후에는 무조건 member(조회만 가능), leader 승격은 admin이 `/admin/users`에서 부여·회수. admin 승격은 앱에 경로를 두지 않고 Supabase SQL로만 한다 |
| 수정 권한 | 콘티/공지사항/캘린더/인명부/곡 마스터의 **모든 편집 API는 leader 이상만 호출 가능**(`require_role("leader")`). 사용자 역할 관리(`/admin/users`)만 admin 전용 |
| 가사 조회 권한 | 자막용 가사 관련 조회(`GET /songs/:id/sections`, `GET /conti/:id/lyrics`)만 예외적으로 **member 이상 로그인 필요**(`require_role("member")`). 저작권 있는 콘텐츠라 다른 조회(콘티/공지/스케줄 등)와 달리 URL만으로는 볼 수 없게 좁혔다(Phase 9, 2026-08-21) |
| 기존 비밀번호 게이트 | `EDIT_PASSWORD` 방식은 **완전히 대체되어 코드에서 제거됨**. 문제가 생기면 Phase 7 교체 커밋을 git revert해 되돌아간다(SDD가 되돌림 경계로 지정한 단일 커밋) — README 최초 버전의 "비밀번호가 최소 기준" 원칙은 이 revert 가능성으로 대체됐다 |
| 비밀번호를 잊었을 때 | **이메일 재설정 링크 대신 관리자 초기화.** `/admin/users`에서 admin이 초기화하면 서버가 무작위 임시 비밀번호를 1회만 화면에 보여주고(관리자도 저장하지 않음), 해당 계정은 로그인 즉시 비밀번호 변경 화면에 강제로 머문다. 본인이 바꾸는 순간부터는 관리자도 새 비밀번호를 모른다 — 이메일 발송(SMTP·스팸함) 문제를 피하기 위한 선택 |
| 알림(푸시/배지) | **구현하지 않음.** 새 콘티/공지가 올라오면 리더십이 카톡방에 링크를 안내하는 기존 방식 유지 |

## 7. 기술 스택

### 확정: FastAPI (Python) + React (반응형 웹) + Supabase (PostgreSQL)

| 레이어 | 선택 | 선택 이유 (요약) |
|---|---|---|
| Backend | **FastAPI** | 혼자 10일 일정에 boilerplate가 적고, **AI/비전 API 연동에서 파이썬 생태계가 압도적으로 유리**하며, Swagger 문서가 자동 생성되어 산출물 요구사항(API 명세서)과 직결된다. |
| Frontend | **React (모바일 우선 반응형 웹)** | **링크 공유만으로 즉시 접속**할 수 있어 테스트 멤버 배포 마찰이 없다. Flutter의 핵심 장점(네이티브 푸시, 스토어 설치)이 **이미 스킵하기로 한 항목들과 정확히 겹친다.** 콘티·공지·캘린더는 텍스트·표·이미지 위주라 웹 성능으로 충분하다. |
| Database | **Supabase (PostgreSQL)** | 스케줄은 관계형 데이터라 PostgreSQL이 적합하고, **파일 저장(Storage)과 Auth가 내장**되어 악보 PDF 업로드와 추후 로그인 확장을 별도 구성 없이 처리할 수 있다. 대시보드로 데이터를 눈으로 확인할 수 있어 SQL 부담도 적다. 22명 규모에는 무료 티어로 충분하다. |

## 부록 A. 표기 안내

- 본 문서에 등장하는 **모든 인물명은 가명**이다. 페르소나(이무진)를 포함해 마이크 배치 예시 등에 쓰인 이름은 실제 팀원과 무관하다.
- 팀에서 실제 운영 중인 구글 스프레드시트(섬김 일정, 인명부)의 **링크와 원본 데이터는 본 문서에 포함하지 않는다.** 구조와 컬럼 구성만 설계 근거로 서술했다.
- **용어**: `싱도`는 신디사이저가 아니라 **"싱어팀 도우미"** 를 뜻하는 팀 내부 용어다. 악기팀 컬럼에 위치하지만 실제로는 사람 역할이다.

## 부록 B. 콘티 원본 형태 예시

목사님이 카톡에 올리는 콘티 이미지의 텍스트 구조 (AI 파싱 대상):

```
260809 4부예배 콘티

1. 삶의 예배_아이자야(G-A)
   (4) A1 A2 B (맞4) A2 B (맞4) (up) B B

2. 전신갑주_잔치공동체(G)
   (8) A B C (4) A B C C (4) C* C** (8)

3. 우리가 주를 더욱 사랑하고_위러브(E)
   (12) A B C (맞4) A* B C (맞8) D C* C bis(주 사랑만이~)*2
```

**구조**: `번호. 곡제목_아티스트(키)` + 다음 줄에 송폼 텍스트.
송폼 표기는 팀 고유 약어(`A1`/`A2`/`B`, `(맞4)`, `(up)`, `bis(가사~)*2`, `Tag`, `x2` 등)로 **불규칙**하며, 이것이 송폼을 자유 텍스트로 저장하기로 한 근거다.
