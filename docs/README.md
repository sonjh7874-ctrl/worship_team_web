# Everyday Worship 제품 정의

> 매주 흩어지는 콘티·악보·섬김 일정을 한곳에 모으는 찬양팀 전용 경량 웹 서비스

이 문서는 제품의 문제 정의, 사용자, 기능 범위와 운영 원칙을 정리한 내부 기준 문서다. 개발 과정과
Phase별 결정은 `전체_로드맵.md`, API 계약은 `API명세.md`, 데이터 구조는 `ERD.md`와 `schema.sql`을 따른다.

**테스트 서비스**: [everydayworship.vercel.app](https://everydayworship.vercel.app)

---

## 1. 문제 정의

찬양팀의 주요 운영 자료는 서로 다른 채널에 흩어져 있다.

- 콘티와 송폼은 매주 카카오톡 이미지로 공유된다.
- 악보 PDF는 콘티와 별도로 공유되어 누락되거나 버전이 달라질 수 있다.
- 월간 섬김 일정은 구글 스프레드시트로 편성한 뒤 캡처 이미지로 공지한다.
- 비정기 행사는 지속해서 확인할 공용 공간이 없어 기억이나 최근 공지에 의존한다.
- 자막용 가사와 참·불참 응답을 리더가 매번 수작업으로 다시 정리한다.

공통 원인은 최신 자료와 수정 가능한 원본을 함께 확인할 단일한 장소가 없다는 점이다. 카카오톡 대화는
쌓이고, 종이 악보는 업데이트되지 않으며, 스프레드시트 원본과 공지용 캡처 이미지는 분리된다.

지금까지 큰 사고가 발생한 것은 아니다. 팀이 그때그때 대응할 수 있었지만, 같은 확인과 정리 작업이
매주 반복된다. 이 서비스는 과장된 위기보다 반복되는 작은 마찰을 줄이는 데 목적이 있다.

## 2. 사용자와 운영 환경

핵심 사용자는 매주 콘티를 정리·배포하고 월간 섬김 일정을 편성하는 주일찬양팀 리더십이다.

- 팀 규모: 약 22명
- 구성: 싱어팀 13명, 악기팀 9명
- 리더십: 리더, 부리더, 싱어팀장, 악기팀장, 회계
- 정기 예배: 주일 4부예배
- 일반 팀원: 리더가 확정한 콘티·스케줄·공지·캘린더를 확인하고 댓글로 소통

리더십의 반복 작업을 줄이면 일반 팀원은 별도 교육 없이 링크를 통해 최신 결과를 확인할 수 있다.

## 3. 제품 범위

제품은 콘티, 공지·월간 스케줄, 캘린더 세 영역을 중심으로 한다. 인명부와 계정 관리는 이 기능을
지원하는 공통 데이터이며, 교회 전체를 관리하는 종합 솔루션으로 확장하지 않는다.

### 3.1 콘티와 악보

목표는 팀원이 한 화면에서 이번 주 연습에 필요한 내용을 확인하는 것이다.

- 콘티 1건은 날짜와 제목을 기준으로 관리한다. 주일예배뿐 아니라 수련회·특별집회도 같은 구조로 다룬다.
- 곡 제목·아티스트·키는 구조화하고, 팀 고유 약어가 불규칙한 송폼은 자유 텍스트로 저장한다.
- 콘티 이미지에서 날짜·제목·곡 순서·키·송폼을 AI로 추출한다.
- AI 결과는 리더가 검수·수정한 뒤 게시한다. 자동 게시하지 않는다.
- 검수 화면은 기존 곡 후보, 유사 곡, 지난 송폼과의 차이를 보여준다.
- 악보 PDF와 원본 콘티 이미지를 Supabase Storage에 보관한다.
- 곡별 가사 구간을 한 번 등록하면 이번 주 송폼 순서에 맞춰 자막용 가사를 조합한다.

AI 인식은 실제 콘티 이미지 5장, 27곡에서 필드 단위 94.8%를 기록했다. 작은 글자의 송폼 약어는
오인식 가능성이 있어 사람 검수를 필수로 유지한다. 프롬프트나 모델을 바꾸면
`backend/tests/ai_parse_baseline.py`로 다시 측정한다.

### 3.2 공지와 월간 스케줄

목표는 공지 원본과 월간 섬김 배정을 한곳에서 관리하는 것이다.

- 공지는 고정글과 일반글로 구분하며, 리더십이 작성·수정한다.
- 월간 스케줄은 월과 주차 단위로 저장하고 선택한 월만 화면에 표시한다.
- 악기팀은 Key1·Key2·드럼·베이스·일렉·싱어팀 도우미·자막·악보를 배정한다.
- 싱어팀은 마이크 1~8번·콰이어·자막·악보를 배정한다.
- 값이 없는 포지션은 조회 화면에서 숨긴다.
- 콰이어와 악보는 여러 명을 배정할 수 있다.

싱어팀 마이크 위치는 매주 고정된다.

```text
        회중석
   4   3   강대상   2   1
   8   7            6   5
        콰이어
```

위 좌표는 프론트엔드 상수로 관리하고, 매주 슬롯에 배정되는 사람만 변경한다. 마이크 위치별 성별 규칙과
참석 가능 여부, 해당 월·연간 배정 횟수를 바탕으로 빈 슬롯의 후보를 제안한다. 제안은 저장된 값을 자동으로
덮어쓰거나 확정하지 않으며, 리더가 검토한 뒤 저장한다. 악기 포지션 자동 배정은 포지션별 가능 데이터가
부족하고 인원 규모가 작아 제외한다.

카카오톡에서 수집한 참·불참 텍스트는 AI가 사람별 데이터로 구조화한다. 싱어팀과 악기팀은 각자 검수·저장하며,
한 팀의 저장이 다른 팀 데이터를 변경하지 않는다. 확정한 결과는 싱어팀 배정 제안의 입력으로 사용한다.

### 3.3 캘린더

캘린더는 정기 주일예배 밖의 비정기 행사와 팀 일정을 확인하는 공간이다.

- 이벤트는 제목·날짜·카테고리·참여 인원·메모·색상으로 구성한다.
- 정기 주일예배 안의 특순은 공지 스케줄을 원본으로 삼아 캘린더에 단방향 동기화한다.
- 인명부에 생년월일이 있는 활동 중 팀원의 생일을 매년 자동 표시한다.
- 동기화된 특순과 생일은 캘린더에서 직접 수정하지 않는다.
- 로그인한 팀원은 공지와 캘린더 이벤트에 댓글을 작성할 수 있다.

동일한 데이터를 두 화면에서 각각 수정하지 않는 것이 원칙이다. 특순은 공지, 생일은 인명부가 각각
source of truth다.

### 3.4 인명부

인명부는 스케줄 배정과 생일 동기화에 사용하는 공통 마스터 데이터다.

- 필수: 이름, 팀 구분, 활동 여부, 성별
- 선택: 생년월일
- 제외: 연락처, 회비, 티셔츠 사이즈, 겸직, 입부일 등 핵심 기능에서 쓰지 않는 개인정보

성별은 마이크 위치 규칙에 사용하므로 필수이며, 생년월일은 입력한 경우에만 캘린더에 반영한다.

## 4. AI 사용 원칙

AI는 반복 입력을 줄이는 보조 수단이며 운영 판단을 대신하지 않는다.

1. AI가 이미지나 텍스트를 구조화해 초안을 제안한다.
2. 기존 데이터와 비교할 수 있는 검수 정보를 함께 제공한다.
3. 권한이 있는 사람이 결과를 수정하고 확정한다.
4. 확정 전 결과를 일반 사용자에게 공개하거나 자동 배정하지 않는다.

송폼 조합과 배정 추천처럼 규칙으로 결정할 수 있는 작업은 AI 대신 결정론적 로직을 사용한다. 예외가 많은
특순·리드보컬·악기 포지션까지 완전 자동화하지 않는다.

## 5. 권한과 공개 범위

| 역할 | 주요 권한 |
|---|---|
| 비로그인 | 콘티·공지·월간 스케줄·캘린더와 댓글 목록 조회 |
| member | 비로그인 권한 + 가사·인명부 조회, 댓글 작성, 본인 정보·비밀번호 변경 |
| leader | member 권한 + 콘티·곡·공지·스케줄·캘린더·인명부 편집, 참·불참과 배정 제안 조회 |
| admin | leader 권한 + 사용자 역할 변경, 비밀번호 초기화, 계정 삭제 |

- 가입 직후 역할은 항상 `member`다.
- `leader` 승격과 회수는 `admin`이 사용자 관리 화면에서 수행한다.
- `admin` 승격은 애플리케이션에 경로를 두지 않고 Supabase SQL로만 처리한다.
- 관리자가 비밀번호를 초기화하면 임시 비밀번호를 한 번만 보여주고, 사용자는 로그인 후 즉시 변경한다.
- 관리자는 자기 계정이나 다른 `admin` 계정을 애플리케이션에서 삭제할 수 없다.
- 새 콘티와 공지 알림은 별도 푸시 대신 기존 카카오톡 링크 공유 방식을 유지한다.

## 6. 기술과 구조

| 레이어 | 기술 | 책임 |
|---|---|---|
| Frontend | React, Vite, React Router | 모바일 우선 UI와 클라이언트 라우팅 |
| Backend | FastAPI, Pydantic | REST API, 인증·권한, 비즈니스 로직 |
| Database | Supabase PostgreSQL | 관계형 데이터와 제약 |
| Auth / File | Supabase Auth, Storage | 로그인·역할 기반 인증과 악보 보관 |
| AI | OpenAI Vision API | 콘티 이미지와 참·불참 텍스트 구조화 |
| Deployment | Vercel, Render | 프론트엔드와 백엔드 분리 배포 |

브라우저는 Supabase DB를 직접 조회하지 않고 FastAPI의 `/api/v1/...` REST API를 거친다. 백엔드는
Router → Service → Repository 계층을 유지하며, API는 현재 63개 엔드포인트로 구성된다.

## 7. 성공 기준과 현재 상태

성공 기준은 소수 테스트 멤버가 실제 콘티와 일정으로 서비스를 사용하고, 기존 카카오톡 공지 방식보다
찾기·확인·수정이 편리한지 정성 피드백을 수집하는 것이다. 전체 22명의 즉시 전환보다 리더십을 포함한
5~10명의 실제 사용을 우선한다.

현재 핵심 기능과 확장 기능, Vercel·Render 테스트 배포까지 완료했다. 모바일 실기기에서 발견한 로그인 버튼,
캘린더 너비와 툴바 문제를 수정했으며 실사용자 테스트와 문서 정리를 진행하고 있다. 상세 구현 현황과
트러블슈팅은 `전체_로드맵.md`를 따른다.

## 8. 제외 범위

| 항목 | 제외 이유 |
|---|---|
| 네이티브 앱 | 링크 공유만으로 접속할 수 있는 반응형 웹이 팀 규모와 테스트 방식에 적합 |
| 푸시·배지 알림 | 기존 카카오톡 링크 안내로 충분 |
| 캘린더 투표 | 카카오톡에서 투표한 뒤 확정 인원만 입력 |
| 가사 자동 검색 | 저작권 문제로 안정적인 무료 원문 API를 사용하지 않음 |
| 교회 전체 관리 기능 | 교인·헌금·출석 관리 등은 찬양팀 운영 범위를 벗어남 |
| 결제 | 핵심 기능과 무관 |
| 연락처 등 상세 인명 정보 | 기능에서 사용하지 않는 개인정보를 저장하지 않음 |
| 마이크 9번 이상 확장 | 실제 무대 구조가 1~8번으로 고정 |
| 악기 포지션 자동 배정 | 포지션별 가능 데이터가 없고 자동화 이득이 작음 |

## 부록. 데이터 표기와 보안

- 문서에 등장하는 인물명과 예시는 모두 가명이다.
- 실제 팀원의 연락처와 운영 중인 구글 스프레드시트 링크·원본 데이터는 저장소에 포함하지 않는다.
- `싱도`는 신디사이저가 아니라 싱어팀 도우미를 뜻하는 팀 내부 용어다.
- Secret과 실제 비밀번호는 코드·문서·테스트 fixture에 기록하지 않는다.
