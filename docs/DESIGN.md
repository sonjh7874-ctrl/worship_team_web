# 청운교회 청년부 주일찬양팀 웹 — 디자인 시스템 및 화면 명세

> 프론트엔드 구현의 단일 디자인 기준 문서다. 기존 디자인 레퍼런스의 정밀한 토큰과 개편 기획안에서 확정한 최신 화면·권한·구현 원칙을 통합했다.
>
> 기준일: 2026-08-24
>
> 대상: 팀원 약 22명이 매주 사용하는 모바일 우선 반응형 웹
>
> 기술 전제: React/Vite, 신규 UI·상태 관리 라이브러리 없음

## 1. 제품 디자인 목표

청년부 찬양팀 전용 경량 도구다. 목표 톤은 **차분하고, 명확하고, 부담 없음**이다.

> 카톡방에 흩어진 콘티·스케줄을 한 곳에 모으는 조용한 도구

마케팅 사이트처럼 강한 첫인상을 만드는 것이 아니라, 사용자가 매주 열어서 이번 주 준비 사항과 배정을 빠르게 확인하고 닫을 수 있어야 한다. 장식보다 정보, 새로운 패턴보다 익숙한 조작, 자동 확정보다 사람의 검토를 우선한다.

### 핵심 원칙

- 일반 팀원은 조회와 댓글 작성, 리더십은 작성·검수·배정·확정이 중심이다.
- 가장 중요한 정보는 “이번 주에 무엇을 준비하고 누가 어디에 배정됐는가”다.
- 정보 밀도를 낮추되 중요한 불참·검수·읽기 전용 상태는 숨기지 않는다.
- 빈 값은 기본적으로 생략하지만, 무대 좌표처럼 구조를 이해하는 데 필요한 빈 슬롯은 유지한다.
- AI 인식과 자동 배정 결과는 제안이며 사람이 확인하고 확정한다.
- 상태는 색만으로 표현하지 않고 텍스트·뱃지·아이콘을 함께 사용한다.
- 최소 터치 영역 44×44px과 모바일 입력 글자 16px을 기준으로 한다.

## 2. 사용자와 권한별 흐름

| 상태·역할 | 중심 행동 | UI 원칙 |
|---|---|---|
| 비로그인 | 공개 콘티·공지·스케줄·캘린더 조회 | 공개 정보와 로그인 필요 기능을 명확히 구분 |
| 팀원(`member`) | 조회, 가사 확인, 댓글 작성·본인 댓글 수정 | 관리 행동을 숨기고 로그인 이점을 안내 |
| 리더십(`leader`) | 콘텐츠 편집, AI 검수, 배정·참불참 관리 | 현재 값 보존, 제안과 확정 구분, 위험 행동 분리 |
| 관리자(`admin`) | 사용자 역할·비밀번호 초기화 관리 | 실수 방지, 1회성 정보와 변경 이력 강조 |

화면에서는 `member`를 팀원, `leader`를 리더십, `admin`을 관리자로 표시한다. 기존 편집 비밀번호 방식은 사용하지 않는다. Supabase Auth와 `member < leader < admin` 역할 체계를 그대로 사용하며 프론트에서 별도 권한 체계를 만들지 않는다.

## 3. 정보 구조와 공통 앱 셸

### 3.1 초기 내비게이션

초기 개편은 `TopBar`로 현재 위치와 핵심 행동을 통일한다.

- 좌측: 뒤로가기 또는 앱 이름
- 가운데 또는 좌측: 현재 화면 제목
- 우측: 화면의 핵심 행동 1개 또는 프로필 메뉴
- 삭제·전체 관리처럼 위험하거나 낮은 빈도의 행동은 상단에 직접 노출하지 않는다.
- 페이지마다 반복되는 `← 메인으로`와 관련 화면 링크는 공통 구조로 정리한다.
- 권한별 메뉴 노출은 기존 `RequireRole`과 `useAuth`를 재사용한다.

하단 고정 내비게이션은 `홈 / 콘티 / 스케줄 / 캘린더 / 더보기`를 후보로 두되 초기에는 구현하지 않는다. 실사용 피드백에서 상단 내비게이션만으로 이동이 불편하다고 확인될 때 다시 결정한다.

### 3.2 반응형 레이아웃

- 모바일 기준: 360~430px
- 태블릿·좁은 데스크톱: 768px
- 데스크톱: 1280px
- 조회 화면 최대 폭: 720px
- 복잡한 편집·운영 화면 최대 폭: 960px
- 모바일 좌우 여백: 16px
- 넓은 화면 좌우 여백: 24~32px
- 단일 `canvas` 배경 위에 카드와 구분선으로 위계를 표현한다.
- 어두운 섹션이나 마케팅형 white → navy 구조는 사용하지 않는다.

규칙:

- primary는 실행 가능한 핵심 행동에만 사용한다.
- accent-warm은 버튼이 아니라 뱃지·라벨·포인트에만 사용한다.
- 한 화면의 warm 강조는 보통 1~2곳으로 제한한다.
- 순수 블랙 `#000`은 본문에 사용하지 않는다.
- 자동 생성·읽기 전용은 neutral 또는 primary-soft와 텍스트 라벨로 나타낸다.

### 4.2 타이포그래피

Family: **Pretendard**. 제목과 라벨은 SemiBold 600, 본문은 Regular 400을 사용한다.

| 역할 | 크기 | 굵기 | 행간 | 용도 |
|---|---:|---:|---:|---|
| Page Title | 22px | 600 | 1.35 | 화면 제목 |
| Section Title | 18px | 600 | 1.40 | 카드 그룹 제목 |
| Card Title | 16px | 600 | 1.45 | 곡·공지 제목 |
| Body | 15px | 400 | 1.55 | 본문·송폼 |
| Control | 15px | 600 | 1.30 | 버튼 텍스트 |
| Label | 13px | 600 | 1.30 | 뱃지·포지션 라벨 |
| Caption | 12px | 400 | 1.40 | 날짜·작성자·메타정보 |
| Mic Number | 15px | 600 | 1.00 | 마이크 슬롯 번호 |

- Hero·Display 크기는 사용하지 않는다.
- 모바일 입력은 브라우저 자동 확대를 피하도록 16px을 사용한다.
- 긴 제목과 이름은 정보 손실 여부에 따라 줄바꿈 또는 말줄임한다.

### 4.3 간격·크기·radius·shadow

- Spacing: `4 · 8 · 12 · 16 · 24 · 32 · 48`
- Radius: sm 6px · md 10px · lg 14px · pill 999px
- 기본 컨트롤 높이: 44px
- 카드 shadow: `0 1px 2px rgba(31, 36, 48, 0.06)`
- 모달·검수 shadow: `0 4px 16px rgba(31, 36, 48, 0.10)`
- shadow는 두 단계 이상 추가하지 않는다.
- 섹션 간격은 24~32px을 기본으로 한다.

### 4.4 포커스와 모션

- 키보드 포커스는 `2px primary` outline과 최소 2px offset으로 표시한다.
- hover만으로 의미를 전달하지 않는다.
- 상태 변화에 긴 애니메이션을 사용하지 않는다.
- `prefers-reduced-motion: reduce`에서 불필요한 전환을 제거한다.
- 오류에 shake 효과를 사용하지 않는다.

### 4.5 Pretendard 제공 방식

- npm 패키지와 외부 CDN을 추가하지 않는다.
- 공식 배포판의 `Pretendard-Regular.woff2`, `Pretendard-SemiBold.woff2`만 로컬 제공한다.
- `font-display: swap`과 `system-ui, sans-serif` fallback을 유지한다.
- OTF 파일은 WOFF2와 중복 배포하지 않는다.
- 폰트와 함께 SIL Open Font License 1.1 사본을 보존한다.

## 5. 공통 컴포넌트

### 5.1 1차 공통화 대상

| 컴포넌트 | 규격 |
|---|---|
| `PageContainer` | 모바일 16px 여백, 화면에 따라 최대 720px 또는 960px |
| Primary Button | primary 배경, 흰색 텍스트, h44, radius sm |
| Secondary Button | 흰색 배경, ink 텍스트, hairline border, h44 |
| Danger Button | 흰색 배경, danger 텍스트·테두리, h44 |
| `Badge` | Label 크기, pill radius, 상태별 soft 배경 + 텍스트 |
| List Card | surface 배경, radius md, shadow 또는 hairline border |
| Detail Card | 흰색 배경, radius lg, hairline border |
| `EmptyState` | surface 배경, muted 텍스트, 가능한 다음 행동 포함 |

### 5.2 필요 시 추가할 후보

두 곳 이상에서 반복되거나 화면에 명확히 필요할 때만 추가한다.

- `IconButton`
- `FormField`, `TextInput`, `Textarea`, `Select`
- `Checkbox`, `Radio`, `SegmentedControl`
- `MonthNavigator`, `SearchField`
- `InlineNotice`, `Callout`
- `LoadingState`, `ErrorState`, `Toast`, `ConfirmDialog`
- `AppShell`, `TopBar`

기존 `ContiDetailView`, `InstrumentPositionGrid`, `MicStageLayout`, `CommentList`를 우선 개선한다. 재사용 가능성이 없는 범용 추상화를 미리 만들지 않는다.

## 6. 공통 상태와 피드백

| 상태 | 표현 |
|---|---|
| 초기 로딩 | 카드 또는 행 스켈레톤, 짧은 안내 |
| 빈 상태 | 무엇이 없는지 + 가능한 다음 행동 |
| 페이지 오류 | 원인 요약 + 재시도 행동 |
| 폼 오류 | 해당 입력 아래 오류 메시지 |
| 저장 성공 | 짧은 toast 또는 인라인 성공 알림 |
| 로그인 필요 | 로그인 이유 + 원래 화면 복귀 흐름 |
| 리더 권한 필요 | 로그인 필요와 구분한 권한 안내 |
| 읽기 전용 | 수정 불가 이유 + 원본 화면 링크 |
| 파괴적 작업 | 대상과 영향을 적은 확인 다이얼로그 |

- 오류 메시지는 사용자를 탓하지 않는다.
- 자동 생성 이벤트는 수정 버튼 대신 원본 화면 이동을 제공한다.
- `window.confirm`은 공통 다이얼로그가 실제로 필요해지는 단계까지 유지할 수 있다.

## 7. 화면별 디자인 명세

### 7.1 홈

- 이번 주 콘티, 가까운 스케줄, 중요 공지 순으로 위계를 만든다.
- 최초 시각 개편에서는 현재 데이터와 마이크 배치도를 제거하지 않는다.
- 각 섹션은 요약 카드와 명확한 전체 보기 행동을 갖는다.
- 리더십 작업 정보는 일반 조회 정보와 구분한다.
- 마이크 전체 배치도를 요약할지는 시각 개편 후 실사용자에게 확인한다.

### 7.2 콘티·AI 검수·자막 가사

- 곡 블록은 순서 번호, 제목, 아티스트·키, 송폼 순서로 읽힌다.
- 송폼은 `pre-wrap`으로 원문 줄바꿈을 보존한다.
- 축복송·퇴장송 등 note는 Warm Tag로 표시한다.
- 악보가 없으면 빈 버튼을 남기지 않고 안내만 보여준다.
- 가사·악보·편집은 역할이 다른 행동으로 구분한다.
- draft는 `검수 필요`, published는 `게시됨`을 함께 표시한다.
- 과거 콘티 검색은 결과 없음 상태를 갖는다.
- AI 검수는 `이미지 인식 → 곡 매칭 → 내용 확인 → 게시` 흐름을 보여준다.
- 기존 곡, 유사 후보, 새 곡 등록과 원본·수정값 차이를 명확히 한다.
- 자막 가사는 로그인 필요 이유를 설명하고 읽기·복사 중심으로 구성한다.
- 해석하지 못한 구간은 `[?]`와 해결 행동을 제공한다.

### 7.3 월간 스케줄·참불참·자동 배정

- 월 탐색은 이전 달, 현재 연월, 다음 달, 오늘 행동의 위계를 통일한다.
- 주차별로 날짜, 특순, 불참, 주요 배정을 먼저 읽을 수 있게 한다.
- 악기 포지션은 2~3열 반응형 그리드이며 값 없는 포지션은 생략한다.
- 불참은 danger-soft callout으로 분리한다.
- 특순은 Warm Tag와 캘린더 원본 관계를 안내한다.
- 월 전체 삭제는 일반 조회 행동에서 분리한다.

참불참 검수는 `월·팀 선택 → 원문 붙여넣기 → 파싱 결과 검토 → 문제 해결 → 확정 저장` 순서로 보여준다. 정상 매칭은 success, 미매칭은 warm, 다른 팀 매칭은 danger, 직접 수정은 neutral로 텍스트와 함께 표시한다. 원문은 기본 접힘이며 `문제 있는 항목만 보기`를 우선 검토한다.

자동 배정은 현재 배정과 제안을 비교하고 변경 슬롯만 강조한다. `month_count`, `year_count`, `skipped`를 근거로 표시하며 기존 저장값과 저장 전 수동 입력을 보존한다. 적용 뒤 최종 저장 전까지 되돌릴 수 있어야 한다. 성별은 서버 내부 판단에만 사용하고 화면에서는 기존 `남 자리`·`여 자리` 라벨만 유지한다.

### 7.4 마이크 배치도

- 앞줄 `4·3·강대상·2·1`, 뒷줄 `8·7·여백·6·5` 좌표를 유지한다.
- 회중석과 무대 방향을 명시하고 줄 간격은 20~24px 이상 둔다.
- 배정 슬롯은 primary-soft, 빈 슬롯은 옅은 테두리 또는 점선으로 표시한다.
- 빈 슬롯도 무대 구조를 위해 유지한다.
- 강대상은 입력 셀이 아닌 faint 라벨 공간으로 표현한다.
- 긴 이름은 말줄임하고 전체 이름을 확인할 방법을 유지한다.
- 콰이어는 하단 중립 pill 목록으로 표시한다.
- 남·여 우선 자리는 색이 아니라 텍스트로 구분한다.

### 7.5 공지사항·댓글

- 고정 공지는 Warm Tag와 accent-warm-soft 배경으로 최상단에 구분한다.
- 목록은 제목, 작성일, 댓글 수 중심으로 표시하고 미리보기는 최대 2줄로 제한한다.
- 상세 본문과 댓글 영역을 구분한다.
- 작성은 리더십, 댓글 작성은 로그인 사용자에게만 노출한다.
- 본인 댓글 행동과 리더십 관리 삭제는 동일한 무게로 노출하지 않는다.
- 수정·삭제는 제목 옆이 아닌 관리 영역에 둔다.

### 7.6 캘린더·자동 이벤트

- 구현된 월간 그리드, 멀티데이 막대, 레인 계산을 유지한다.
- 월 이동, 오늘, 카테고리 필터의 위계를 정리한다.
- 필터 chip, 선택 날짜 목록, `+N개` 요약은 모바일 검증 후 필요할 때 도입한다.
- 이벤트는 색뿐 아니라 아이콘·카테고리·자동 라벨을 사용한다.
- 생일은 birthday 색과 `생일`, 자동 특순은 연결 의미와 `자동`을 병기한다.
- 자동 특순은 스케줄, 생일은 인명부로 이동하는 안내 카드를 갖는다.

### 7.7 인명부

- 전체·악기팀·싱어팀 필터와 이름 검색을 제공한다.
- 활동 중 인원을 우선하고 비활동 인원을 구분한다.
- 이름, 팀, 성별, 생일 월·일, 활동 상태를 일정한 행으로 표시한다.
- 하드 삭제보다 비활성 전환을 기본 행동으로 둔다.
- 생년월일 변경과 생일 자동 이벤트 관계를 안내한다.
- 모바일 편집이 복잡하면 별도 편집 카드를 검토한다.

### 7.8 곡·가사 관리

- 리더십 운영 메뉴에 두고 검색을 가장 먼저 제공한다.
- 사용 횟수, 가사·악보 여부를 텍스트 뱃지로 표시한다.
- 가사 구간은 구간명과 내용을 묶은 카드로 구성한다.
- 순서 이동은 신규 의존성 없이 44px 버튼으로 제공한다.

### 7.9 인증 화면

- 인증 폼은 좁은 단일 카드로 만든다.
- 오류는 관련 필드 가까이에 표시한다.
- 강제 비밀번호 변경은 이유를 먼저 설명한다.
- 내 정보에서 표시 이름, 이메일, 역할, 비밀번호 행동을 구분한다.
- 로그인 후 원래 화면으로 돌아가는 흐름을 보존한다.

### 7.10 사용자 관리

- 활성·비활성 사용자를 구분한다.
- 현재 역할과 변경 행동을 분리한다.
- 비밀번호 초기화는 대상과 영향을 확인하는 위험 작업으로 표시한다.
- 임시 비밀번호는 1회성 callout과 복사 행동을 제공한다.
- 변경 이력은 기본 접힘으로 둔다.
- 불가능한 행동은 숨기거나 이유를 설명한다.

## 8. 접근성과 검증 기준

- 주요 터치 영역 44×44px 이상
- 모바일 입력 글자 16px
- 명확한 키보드 포커스 링
- 색 외에 텍스트·아이콘으로 상태 전달
- 아이콘 버튼에 접근 가능한 이름 제공
- label과 입력, 오류 메시지를 연결
- DOM 읽기 순서와 시각적 순서 일치
- 200% 확대와 좁은 화면에서 핵심 행동 보존
- 긴 이름·제목, 일정 중첩, 빈 데이터, 로딩, 오류 검증
- `prefers-reduced-motion` 대응

필수 뷰포트는 360px, 390px, 430px, 768px, 1280px이다. 스크린샷만으로 키보드 조작, 스크린리더 읽기 순서, 전체 명도 대비를 확정하지 않고 실제 동작을 별도로 점검한다.

## 9. Voice

차분하고 친근하되 존댓말을 유지한다. 마케팅 문구가 아니라 안내문처럼 쓴다.

- “악보가 아직 없어요”
- “이번 주 콘티가 게시되지 않았어요”
- “비밀번호가 일치하지 않아요”
- “인명부에서 생년월일을 수정해주세요”

사용자를 탓하는 문구, 명령조, 이모지·느낌표 남발을 피한다. 싱도, 콰이어, 송폼 같은 팀 내부 용어는 그대로 사용한다.

## 10. Do / Don’t

### Do

- Pretendard SemiBold 제목, Regular 본문
- primary는 행동과 현재 위치에만 사용
- warm은 뱃지·특별 상태에만 사용
- 빈 데이터는 생략하되 구조상 필요한 빈 슬롯은 유지
- 불참·오류는 danger와 텍스트로 강조
- 자동 생성·제안·읽기 전용의 이유 표시
- 실제 무대 좌표 유지

### Don’t

- 대형 마케팅 Hero 타이포
- 화려한 그라디언트와 다단계 shadow
- 의미 없는 새 강조색 추가
- 전체 화면 모달 남용
- 순수 블랙 본문
- 권한 없는 관리 행동 노출
- 자동 제안을 확정값처럼 표현

## 11. 구현 단계와 경계

기능 버그·API 정합성·배포 설정 수정은 디자인 작업과 별도 작업·별도 커밋으로 처리한다. 각 단계는 독립적으로 완료하고 뒤 단계를 하지 않아도 서비스가 정상 동작해야 한다.

### 0단계 — 문서·폰트·토큰 기반

- 본 문서로 디자인 명세 통합
- Pretendard WOFF2와 라이선스 적용
- CSS 변수와 전역 기본값 정의
- 개별 페이지 구조와 스타일은 변경하지 않음

### 1단계 — 최소 공통 컴포넌트

- `PageContainer`, `Button`, `Badge`, `Card`, `EmptyState`

### 2단계 — 공통 앱 셸과 TopBar

- 페이지 최대 폭과 패딩, 중복 뒤로가기·메뉴, 제목과 핵심 행동 통일
- BottomNav는 보류

### 3단계 — 핵심 조회 화면 시각 체계

기존 상태·라우팅·정보 구조를 유지한 채 `홈 → 콘티 → 스케줄 → 공지 → 캘린더` 순서로 적용한다.

### 4단계 — UX 구조와 상호작용

- 공통 로딩·오류·성공 상태
- 댓글과 마이크 배치 세부 조정
- 필요성이 확인된 탭·카드 접기·캘린더 날짜 목록·필터 chip·`+N개` 요약
- 각 기능을 별도로 도입하고 회귀 검증

### 5단계 — 리더십 편집·검수

- 콘티 편집·AI 검수, 스케줄 편집·자동 배정, 참불참, 공지·캘린더 편집, 인명부, 곡·가사 관리

### 6단계 — 인증·관리자·전체 QA

- 로그인·회원가입·내 정보·비밀번호 변경, 사용자 관리
- 전체 뷰포트·권한·키보드·대비·긴 콘텐츠 검증

## 12. 구현 전 확인 사항

1. 홈의 마이크 전체 배치도를 유지할지, 요약 후 스케줄로 이동시킬지 실사용자에게 확인한다.
2. 모바일 캘린더 선택 날짜 목록과 `+N개` 요약이 실제 일정 밀도에서 필요한지 확인한다.
3. 운영 DB 성별 백필·생일 마이그레이션 상태가 빈 상태에 미치는 영향을 확인한다.
4. 3단계 시각 개편 뒤 4단계 UX 변경의 우선순위를 실사용 피드백으로 정한다.

## 13. 디자인 개편 완료 기준

- 모든 페이지가 공통 앱 셸 안에서 동작한다.
- 모바일에서 주요 화면 사이를 일관되게 이동할 수 있다.
- 핵심 버튼과 입력 요소가 44px 이상이다.
- 로딩·빈 상태·오류·성공·권한 상태가 공통 규칙을 따른다.
- 권한 없는 관리 행동이 노출되지 않는다.
- 자동 생성·제안·읽기 전용의 이유가 표시된다.
- 캘린더·마이크 배치·자동 제안이 작은 화면에서도 핵심 정보를 잃지 않는다.
- 개편 대상 화면의 인라인 스타일이 공통 클래스 또는 컴포넌트로 이전된다.
- Pretendard WOFF2 두 굵기만 배포되고 라이선스가 보존된다.
- `npm run build`와 `npm run lint`가 통과한다.
- 360px, 390px, 430px, 768px, 1280px 검증 기록이 남는다.
